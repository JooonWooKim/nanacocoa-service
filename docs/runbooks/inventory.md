# 재고·품절 관리

## 수량과 판매 상태

`stockQuantity`는 새 주문이 확보할 수 있는 수량이고 `reservedQuantity`는 이미 주문이 확보한 수량입니다. 관리자는 `/inventory.html`에서 판매 가능 수량을 조정하고 `ON_SALE`/`STOPPED`를 선택합니다. `ON_SALE`이면서 판매 가능 수량이 0이면 공개 API의 `availability`는 `SOLD_OUT`입니다. 예약 수량은 관리자 조정으로 덮어쓰지 않습니다.

공개 상품 목록·상세 응답은 `availability`만 노출하고 재고 수량·예약 수량·버전은 포함하지 않습니다. 관리자 화면은 DB 관리자 권한을 확인하는 `GET /api/products/inventory`를 사용합니다. 구매 수량의 재고 검증은 서버 주문 생성 시 수행합니다.

재고 저장은 `PUT /api/products/{productId}/inventory`로 `stockQuantity`, `saleStatus`, `expectedVersion`을 보냅니다. 서버는 현재 DB의 관리자 권한과 상품 행 잠금을 확인하고 기대 버전이 다르면 `PRODUCTS_07` / HTTP 409로 거부합니다. 새로고침해 최신 재고를 확인한 뒤 재입력합니다. 신규 상품은 0개·판매 중지로 생성됩니다.

## 주문·결제 정책

- 주문 생성 트랜잭션이 상품 ID 오름차순으로 상품 행을 잠근 뒤 재고를 차감하고 예약 수량을 증가시킵니다. 복수 상품 중 하나라도 실패하면 주문 전체가 롤백됩니다.
- 신규 주문은 `stockState=RESERVED`이며 생성 시점부터 15분 후 만료됩니다. 1분 주기 작업이 최대 100개의 `CREATED` 주문을 처리합니다. `order.inventory.expiration-enabled=false`로 작업을 끌 수 있습니다. `order.inventory.expiration-delay`의 기본값은 60000ms입니다. 만료 기한 자체는 현재 15분 고정입니다.
- 승인 준비는 주문 행 잠금 아래 만료·재고 상태를 확인하고 `PAYMENT_PENDING`으로 전환합니다. 만료 작업과 승인 준비는 동일 주문 행 잠금으로 직렬화됩니다. `PAYMENT_PENDING`은 만료시키지 않으며 조회 타임아웃·불확실 결과 중에도 예약을 유지합니다.
- 승인 성공은 예약 수량을 판매 확정하고 `SOLD`로 바꿉니다. 확정 실패·보상 취소는 `RELEASED`로 바꾸며 한 번만 예약 수량을 복원합니다. 주문은 기존 결제 재시도 계약을 위해 `CREATED`로 돌아갑니다.
- `POST /api/orders/{orderId}/reservation`은 소유자만 호출할 수 있는 재시도 전 재고 확보 API입니다. 기한은 연장하지 않으며 서버 승인 API도 다시 확인합니다. 기한 만료 또는 다른 고객의 재고 선점 시 새 결제를 시작할 수 없습니다.
- `POST /api/orders/{orderId}/cancel`은 소유자의 `CREATED` 주문만 취소합니다. 결제 확인 중에는 결과를 먼저 확인하고, 결제 완료 주문은 주문 상세의 취소·반품 신청과 운영 처리를 사용합니다. 새 직접 결제 취소 API는 신청을 요구하며 기존 취소의 재전송·복구는 유지합니다. 취소·만료 재실행은 재고를 중복 복원하지 않습니다.
- 결제 승인 이후의 취소/반품은 자동으로 판매 가능 재고를 늘리지 않습니다. 미출고 또는 회수된 상품이 재판매 가능한지 확인한 운영자가 `POST /api/orders/{orderId}/restock`에 `reason`을 보내거나 관리자 화면에서 주문 번호와 검수 사유를 입력합니다. 전체 취소가 완료된 `CANCELED`/`SOLD` 주문만 전체 수량을 한 번 재입고하고 `RETURNED`로 전환합니다. 파손·미회수 상품은 이 동작을 수행하지 않습니다. 부분 반품/부분 재입고는 이 기능의 범위가 아닙니다.
- 승인/취소/보상 복구는 기존 `PaymentTransactionalService` 경계를 통해 재고와 주문을 같은 트랜잭션에 반영합니다. 확정되지 않은 결제에 대해 예약을 임의로 해제하지 않습니다.
- 승인 복구 조회에서 결제 키·주문 번호·금액이 일치하고 `ABORTED` 또는 `EXPIRED`이면 결제를 실패 처리하고 예약을 해제합니다. 조회 정보가 일치하지 않으면 예약을 유지한 채 기존 복구 동작을 다시 예약합니다.

## 배포 전 데이터 이행

V5는 기존 상품을 **재고 0개·판매 중지**로 이행합니다. 관리자 실사 후 실제 판매 가능 수량을 입력하고 판매 중으로 바꿔야 합니다. 기존 주문에는 `LEGACY`를 부여하여 임의의 과거 재고를 만들지 않습니다.

1. 주문·결제 쓰기를 멈추고 기존 진행 중 승인·취소·복구 작업을 정리합니다. 새/구버전 인스턴스를 혼합 운영하지 않습니다.
2. DB 백업 후 V5를 적용하고 JPA 스키마 검증을 확인합니다. 기존 마이그레이션 파일은 수정하지 않습니다.
3. 기존 `CREATED` 주문의 새 승인 시작은 차단됩니다. 고객에게 새 주문을 만들도록 안내하고 과거 미결제 주문은 소유자 취소 API 등으로 정리합니다. `LEGACY` 주문은 예약 수량을 자동 해제하거나 재입고하지 않습니다.
4. 기존 `PAYMENT_PENDING` 결제의 복구는 허용하지만 과거 상품 재고는 자동 차감하지 않습니다. 미정산 결제·기존 판매·반품을 먼저 감사하고 판매 가능 수량에 반영해야 합니다.
5. 관리자 화면에서 실제 재고를 등록한 뒤 주문을 재개합니다. 공개 목록·상세·checkout에서 서버의 품절·판매 중지 상태를 확인합니다.

V5 적용 후 구버전으로 바로 되돌리면 재고를 무시하는 주문이 생깁니다. 장애 시 주문 쓰기를 차단하고 DB 스냅샷/정방향 보정 계획을 검토합니다. 재고 컬럼을 삭제하거나 기존 결제를 일괄 초기화하지 않습니다.

## 검증

`InventoryIntegrationTest`는 기본 H2에서 외부 제공자 호출 없이 동시성·권한·결제 전이·만료·재입고를 검증합니다. 실제 MySQL 검증에는 **별도 임시 DB만** 지정합니다. 테스트는 임의 이름의 테스트 회원·상품·주문을 생성하므로 운영/공유 DB를 지정하면 안 됩니다.

```sh
INVENTORY_TEST_DB_URL='jdbc:mysql://127.0.0.1:<임시포트>/inventory_test?allowPublicKeyRetrieval=true&useSSL=false' \
  ./gradlew test --tests '*InventoryIntegrationTest' --rerun-tasks
```

테스트 URL은 사용자 소유 MySQL에 연결하지 않는 별도 컨테이너를 대상으로 하며 username=root/password 빈 문자열인 일회성 로컬 테스트 환경을 가정합니다. 네트워크는 loopback에만 바인딩하고 완료 후 해당 임시 컨테이너만 정리합니다. 실제 PG/S3 호출은 하지 않습니다.
