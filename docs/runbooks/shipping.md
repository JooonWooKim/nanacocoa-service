# 배송 운영 절차

## 운영 설정

운영 담당자가 승인한 택배사 코드, 표시 이름과 송장 형식, 조회 주소를
Spring 설정 `shipping.carriers`에 등록합니다. 설정에 택배사가 없으면
신규 출고와 송장 변경을 등록할 수 없습니다. 아래 값은 테스트용 예시입니다.

```yaml
shipping:
  carriers:
    example:
      name: 예시 택배
      tracking-pattern: '[0-9]{10}'
      tracking-url: 'https://carrier.example.test/track/{tracking}'
```

조회 주소는 고정된 HTTPS 호스트와 `{tracking}` 치환 위치를 사용합니다.
조회 주소를 생략하면 고객 화면에서 송장 번호를 복사할 수 있습니다. 송장 번호는
최대 64자의 영문·숫자·하이픈이고 택배사별 정규식도 통과해야 합니다.

## 출고와 배송 완료

1. 관리자로 로그인해 메뉴에서 **배송 관리**를 엽니다. 기본 목록에는 오래된 배송 준비 주문부터 표시됩니다.
2. 주문 상세의 수령인·주소·품목을 대조해 포장합니다. 택배사, 송장 번호와 사유를 저장합니다.
3. 등록 성공 또는 상세 재조회로 배송 중 상태와 송장을 확인한 뒤 물품을 인계합니다. 저장 결과가 불명확하면 상세를 재조회하거나 같은 화면에서 동일 입력으로 재시도합니다.
4. 잘못 등록한 택배사·송장은 상세에서 사유와 함께 바로잡습니다. 택배사에서 배송 완료를 확인한 뒤 완료를 기록합니다.
5. 등록 후 인계 실패, 오배송, 배송 완료 오기록은 물품과 택배사 기록을 대조하고 운영 정책에 따라 고객에게 안내합니다. 송장 정정은 최초 출고 일시를 유지합니다.

출고 확정 시점에 구매자의 직접 결제 취소가 차단됩니다. 취소 결과 확인 중에는
출고가 보류됩니다. 출고 후에는 확정된 고객 문의 절차를 안내합니다.
배송 처리는 재고나 환불 금액을 변경하지 않습니다.

## V6 적용과 과거 주문 대조

V6 적용 전 주문·결제 쓰기를 일시 중단하고, 구버전과 신버전을 섞어 운영하지
않습니다. 마이그레이션은 기존 주문을 확인 대상으로 표시합니다. 이 단계에서
송장이나 배송 완료 기록은 생성되지 않습니다.

- 출고 보류 목록에서 주문을 열고 실제 결제·택배 기록과 대조합니다.
- 미출고 결제 주문은 **과거 주문 미출고 확인**과 사유를 저장합니다. 이후 결제·재고·배송 조건이 맞으면 출고할 수 있습니다.
- 출고나 완료가 확인된 주문은 주문 번호 검색과 **전체** 필터에서 열 수 있습니다. 확인된 택배사·송장·시각·사유를 등록합니다. 과거 시각은 애플리케이션의 주문 시각과 같은 시간대로 입력합니다.
- 출고 여부를 알 수 없는 주문과 `LEGACY` 재고 주문은 운영 담당자에게 이관합니다. 배송 여부 확인이 끝날 때까지 새 결제 취소도 보류합니다.

운영 반영 전에 배송비·배송 가능 지역·출고 기준·고객 문의 절차를 승인합니다.
배송 데이터가 기록된 뒤 앱을 롤백할 때는 주문·결제 쓰기를 중단하고 출고 이후
직접 취소가 가능한 구버전의 영향부터 검토합니다. 배송 데이터와 이력을 보존합니다.
