# 취소·반품·환불 운영

상태: feature/26 구현 기준 · 운영 정책 미승인 · 기본 비활성

## 정책 설정과 활성화 조건

정책 담당자가 기간·비용·회수·검수·재신청과 문의 경로를 승인하기 전에는 활성화하지 않는다.
기술 구현과 정책 승인은 별도다. [PRD](../product-specs/cancellation-return-prd.md)와
[출시 PRD](../product-specs/commerce-launch-prd.md)에 승인자·시각·버전·결정을 기록한다.

기본 설정은 다음과 같다. 실제 운영값을 제공하는 예시가 아니다.

```yaml
returns:
  policy:
    enabled: false
    version: ""
    approved-by: ""
    approved-at: ""
    guidance: ""
    window-days: 0
    allow-in-transit: null
    allow-reapply: null
    refund-after-failed-inspection: null
```

- enabled=true와 비어 있지 않은 version(64자 이하), approved-by, 고객에게 표시할 guidance가 필요하다.
- approved-at은 현재보다 과거인 offset 포함 ISO-8601 시각이어야 한다.
- window-days는 승인된 양의 반품 기간(최대 3650일)이다. 배송 완료 시각부터 계산하며,
  배송 중 신청이 허용된 경우 배송 완료 전에는 출고 시각을 기준으로 한다.
- allow-in-transit, allow-reapply, refund-after-failed-inspection은 각각 배송 중 신청,
  반려 후 재신청, 재판매 불가 검수 후 환불 허용 여부를 승인한 명시적 true/false다.
- 설정 누락·비활성·유효하지 않은 값은 RETURN_01/503으로 신규 신청·처리를 차단한다.
  조회와 기존 미확정 결제 복구는 유지한다. 처리 중 신청의 정책 버전을 변경하면 신규 처리를 보류한다.
  이전 버전 신청의 대조·처리를 마친 뒤 정책 버전을 전환한다.
- 이 기능은 주문 전체 결제액만 환불한다. 별도 비용 수납은 승인된 운영 절차를 사용하고,
  결제액에서 비용을 공제해야 하면 부분 환불을 포함한 범위를 다시 정해야 한다.
- 설정 활성화가 Toss 운영 결제나 자동 복구를 활성화하지 않는다. PG 설정은
  [결제 환경 절차](payment-environment.md)를 별도로 따른다.

## 구매자와 운영자 흐름

1. 구매자는 orders.html 상세에서 서버가 허용하는 전체 취소·반품을 신청한다.
   신청 사유·정책 버전·진행·반려 사유·환불·재입고를 조회한다.
2. 운영자는 returns.html에서 주문 번호·유형·상태로 조회한다. 현재 DB 관리자 권한이 필요하다.
3. 취소는 승인 후 미출고 상품을 검수한다. 반품은 승인 → 회수 시작 → 회수 완료 → 검수를 기록한다.
   검수 시 재판매 가능 여부와 정책에 따른 환불 가능 여부를 각각 입력한다.
4. 환불 가능 검수 후 운영자가 전액 환불 실행을 명시적으로 선택한다.
   반려 사유는 고객에게 공개되며 다른 작업 사유·담당자 ID는 운영자만 볼 수 있다.
5. 환불 완료는 PG 취소 확인과 DB 반영 뒤 표시한다. 확인 중이면 기존
   payment-operations.html의 해당 취소 거래를 조회·복구한다. 새 환불을 추가 생성하지 않는다.
6. 환불 완료·재판매 적합이면 검수 재입고를 명시적으로 수행한다. 이력과 재고는 같은 트랜잭션이며
   중복 실행은 한 번만 반영한다. 미회수·파손 상품은 재판매 가능한 것으로 기록하지 않는다.

신청·운영 작업은 요청 키와 내용을 저장한다. 응답을 잃으면 먼저 조회하고, 동일 내용의 명시적
재시도는 같은 키를 사용한다. 화면 새로고침·로그인 복귀는 조회만 한다. 이전 revision이나
같은 키의 다른 내용은 409다. 조회는 PG를 호출하지 않는다.

## 기존 경계와 장애 대응

- 취소 접수 뒤 판단·환불 중에는 출고가 보류된다. 출고가 먼저 확정됐으면 반품 경로를 사용한다.
- 신규 직접 결제 취소는 RETURN_03/409로 안내한다. 기존 취소의 일치하는 재전송·복구는 유지한다.
  결제 비활성은 기존 PAYMENT_11/503을 유지한다.
- 연결된 신청이 있는 주문은 직접 재입고 API에서도 환불 완료·적합 검수를 검증한다.
  도입 전 취소된 주문은 기존 운영자 수동 검수 재입고 흐름을 사용한다.
- LEGACY 재고·출고 미확인 주문은 신규 신청을 보류하고 [배송 대조](shipping.md)를 진행한다.
  과거 결제 거래의 복구를 막거나 신청·검수 기록을 추정 생성하지 않는다.
- 외부 응답 불일치, 타임아웃, PG 성공 뒤 DB 반영 실패는 확인 중으로 남긴다.
  기존 거래 키로 복구하고 강제로 완료·재입고하지 않는다. 확정 실패 뒤 새 환불은 명시적 운영 작업이다.
- CSRF·세션 오류는 상태를 다시 조회한 후 수행한다. 일반 회원에게 운영 정보가 노출되지 않아야 한다.
  로그·증거에 고객 원문, 세션, 결제 키, PG 오류 원문을 남기지 않는다.

## 검증과 롤백

ReturnRequestIntegrationTest는 모의 PG와 H2 또는 격리된 MySQL 8.4에서 신규 V8·JPA 검증,
정책 비활성, 권한·CSRF·개인정보, 출고 경합·중복 신청·환불·재입고·타임아웃 복구를 검증한다.
FlywayMigrationTest는 기존 주문의 데이터 보존을 확인한다. 실제 Toss Payments·S3는 호출하지 않는다.
브라우저 증거와 남은 검증은 [실행 기록](../exec-plans/completed/issue-26-return-implementation.md)에 기록한다.

롤백 시 정책을 비활성화해 신규 작업을 차단하고 이미 접수된 결제 취소는 기존 복구 경로로 대조한다.
V8과 신청·처리·취소 이력을 보존한다. 직접 취소를 허용하는 구버전 앱으로의 롤백은 정책 우회 위험을
먼저 검토한다. 기존 Docker 스택·데이터·볼륨을 삭제하지 않는다.
