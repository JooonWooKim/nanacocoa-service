## 목표

구매 회원은 바로 구매 후 주문·결제 결과를 다시 확인하고 배송 조회와 취소·반품 신청을 할 수 있다. 운영자는 결제가 확정된 주문을 출고하고, 출고 여부와 반품 검수 결과에 따라 환불·재입고를 처리할 수 있다. 첫 공개 출시는 아래 P0 인수 기준 충족을 목표로 한다.

1. SEC와 PAY의 모의 PG·운영 활성화 설정을 먼저 진행한다. 배송 범위·요금, 취소·반품 조건, 약관·동의 원문 확정은 병행한다.
2. 배송·반품 정책이 확정되면 병합된 ORDER·SHIP을 기반으로 RETURN을 구현한다. 구매자 주문 상세와 관리자 처리 화면을 연결하고 결제 취소·복구와 재입고를 연동한다. 승인된 POLICY 원문 게시와 동의 이력 구현은 병행한다.
3. 운영 택배사와 실재고를 등록하고 V6 배송 확인 대상인 기존 주문을 점검한다. 구매·결제부터 배송·취소·반품·환불까지 고객 화면과 서버 상태를 대조하고, 출시 승인 기준을 충족한 뒤 P1을 진행한다.

첫 출시 범위는 회원 바로 구매, 주문당 송장 1개, 주문 전체 취소·반품·환불로 제안한다. 출시 메뉴는 실제 동작하는 화면과 문의 경로로 연결한다. 부분 출고·부분 환불, 장바구니, 자동 배송 상태 수집은 후속 범위에서 검토한다.

## STOCK · 재고와 품절 출시 검증

- 상품의 판매 상태는 공개 화면에 표시하고, 수량·예약 수량·버전은 관리자만 조회한다. 주문을 만들 때 판매 가능 재고를 예약한다. 현재 미결제 예약 만료는 15분이며 승인 결과가 불확실한 동안에는 예약을 유지한다.
- 승인 성공은 예약을 판매로 확정한다. 미결제 취소·만료, 승인 확정 실패 및 승인 보상 완료 시 예약을 한 번 해제한다. 결제 완료 후 전체 취소된 상품은 운영자가 검수 후 한 번 재입고한다.
- 출시 검증은 마지막 수량 동시 주문, 복수 품목의 전체 롤백, 승인과 만료의 경합, 검수 재입고 중복 방지를 포함한다. V5가 기존 상품을 재고 0개·판매 중지로 이행하므로 상품별 실재고 등록과 판매 활성화를 확인한다. [재고 운영 절차](../runbooks/inventory.md)

## P0 · 출시 전 요구사항

### ORDER · 주문 목록과 상세

- 마이페이지에서 본인 주문을 최근순으로 페이지 단위 조회한다. 목록에 주문 번호·일시·대표 상품·합계·상태를 표시하고 주문 없음, 조회 실패, 세션 만료 시 후속 행동을 안내한다.
- 상세에서 주문 당시 상품명·단가·수량·합계, 주문 당시 배송 정보, 결제 결과와 배송·취소·반품 상태를 보여준다. 결제 확인 중이면 새 결제를 유도하기 전에 주문에서 결과를 다시 확인할 수 있게 한다. 서버가 허용하는 후속 행동을 화면에 표시한다.
- **인수 기준** — 새로고침·재로그인 시 DB에 저장된 주문과 최신 상태를 조회한다. 상품 정보와 회원 배송지를 수정해도 과거 주문 정보는 그대로 조회된다. 미인증과 타인 주문 접근을 서버에서 거부하며 타인에게 주문 존재 여부나 배송 정보가 드러나지 않는다. 이전 버전의 주문은 실제 저장된 정보로 조회한다.

### SHIP · 관리자 출고와 구매자 배송 조회

[배송관리 구현 PRD](shipping-management-prd.md)에 상태 전이, 화면·서버 계약,
취소와의 경합, 출시 검증 기준을 정의한다.

- 관리자는 주문 번호·배송 상태로 배송 준비 주문을 찾아 출고와 배송 완료를 기록한다. 출고에 택배사와 송장 번호를 요구하고 등록·수정 이력에 담당자, 시각, 사유를 남긴다. 배송 준비, 배송 중, 배송 완료는 주문·결제 상태와 별도로 표시한다.
- 구매자는 본인 주문에서 배송 상태, 택배사, 송장 번호와 출고 이후 제공되는 조회 링크를 확인한다. 운영자가 상태를 갱신하는 방식으로 첫 출시를 제안한다.
- **인수 기준** — 결제 확정 주문만 출고할 수 있고 미결제·결제 확인 중·취소 처리 중 주문의 출고를 서버가 차단한다. 동시 출고·취소 요청으로 출고와 출고 전 취소가 모두 확정되는 경우가 없어야 한다. 일반 회원의 운영 API 호출은 거부되고, 송장 수정 내역은 구매자 조회 화면에 반영된다.

### RETURN · 취소, 반품, 환불

- 미결제 주문은 기존 주문 취소 API로 처리한다. 결제 완료 후 출고 전에는 전체 취소를, 출고 후에는 운영 정책에 따른 전체 반품을 신청할 수 있다. 고객 화면은 신청 사유, 반려 사유, 회수·검수 진행, 환불 확인 중·완료·실패 상태와 다음 행동을 안내한다.
- 관리자는 신청 목록에서 출고 기록을 확인하고 승인·반려, 반품 접수·회수·검수 결과를 처리한다. 운영자 권한과 처리 가능 상태를 검증한 뒤 기존 결제 취소·복구 로직을 재사용한다. 고객의 직접 API 요청에도 같은 출고·취소 정책이 적용된다.
- 반품 환불과 재입고를 각각 기록한다. 환불은 제공자 취소가 확인되면 완료 처리한다. 판매 가능 상품은 전체 취소 확정과 운영자 검수를 거쳐 기존 재입고 흐름으로 반영한다.
- **인수 기준** — 출고 전 취소, 출고 후 반품 승인·반려, 환불 타임아웃 후 복구, 검수 불합격을 재현한다. 새로고침·중복 제출·복구 중에도 동일 요청은 환불과 재입고를 각각 최대 한 번만 발생시킨다. 환불 완료와 재입고 가능 여부를 고객·관리 화면에서 각자의 권한 범위로 확인할 수 있다.

### PAY · 구매부터 결제 결과 복구까지 검증

- 바로 구매 → 배송 정보 입력 → 서버 가격으로 주문 생성 → Toss 콜백 → 결제 승인 → 주문 상세까지 연결한다. 성공·실패·확인 중 화면은 서버에 저장된 주문·결제 상태를 기준으로 표시한다. 주문 제출을 재전송해도 동일 구매 시도가 주문·예약을 추가로 생성하지 않도록 한다.
- 자동화 테스트는 모의 결제 제공자로 실행한다. 운영 결제는 운영 프로필과 명시적 활성화 설정에서만 가능하게 하고 환경별 키·대상 설정을 검증한다. 오래 머무르는 결제·환불 확인 중 상태를 운영자가 찾고 복구 결과를 확인할 수 있어야 한다. [기술부채 NC-OPS-001/002](../exec-plans/tech-debt-tracker.md)
- **인수 기준** — 아래 시나리오마다 고객 화면과 서버의 주문·결제·재고 결과를 대조한다. 테스트에는 가상 회원·주문을 사용한다.

| 시나리오 | 기대 결과 |
| --- | --- |
| 정상 승인 | 주문 상세에 결제 완료와 서버 금액 표시, 예약은 한 번 판매 확정 |
| 명시적 거절·승인 만료 | 실패 안내, 예약 한 번 해제, 재시도 가능 여부는 주문·재고 상태로 판정 |
| 승인 타임아웃 | 결과 확인 중 표시, 예약 유지, 재조회·복구 후 확정 상태로 수렴 |
| 주문 제출·성공 콜백 반복 | 동일 시도에 주문·예약·최종 승인 중복 없음 |
| 잘못된 금액·주문 또는 다른 회원 주문 | 승인과 판매 확정 차단, 적절한 오류 안내 |
| 세션 만료·새로고침·앱 재시작 | 로그인 복귀와 주문 재조회로 진행 상태 확인, 대기 시도 복구 |
| 결제 완료 후 전액 취소 | 제공자 취소 확정과 주문 환불 상태 일치, 재입고는 검수 절차에 따름 |

### SEC · 세션 보안

토큰 API와 화면 오류 복구 계약은 [세션 보안 구현 PRD](session-security-prd.md)를 따른다.

- 세션을 사용하는 브라우저의 상태 변경 요청에 CSRF 보호를 적용한다. 로그인·로그아웃·회원정보 수정·주문·결제·운영 관리 화면을 포함해 정상 요청에서 토큰을 전달하고, 토큰 누락 또는 만료에 대한 복구 동선을 제공한다.
- 로그아웃은 POST로만 처리하고 기존 세션을 폐기한다. 로그인 성공 시 세션 ID를 회전하고 이전 세션의 마이페이지 본인 확인 권한을 초기화한다. 로그인으로 복귀한 결제 흐름은 주문 소유권과 결제 상태를 다시 검증한다.
- **인수 기준** — 유효 요청은 성공하고 CSRF 토큰 누락·오류 요청은 거부된다. GET 로그아웃 요청은 인증 상태를 바꾸지 않는다. 로그인 전 ID와 로그아웃한 세션으로 보호 자원에 접근할 수 없다. 기존 회원 본인 확인과 결제 복귀 흐름을 회귀 검증한다. [세션 보안 구현·검증 기록](../exec-plans/completed/session-security.md)

### POLICY · 서비스 안내, 약관, 가입 동의

- 가입·checkout·푸터에서 운영자가 확정한 서비스 약관·개인정보 안내·판매자와 문의처·배송비와 출고 기준·취소/반품/환불 정책을 확인할 수 있게 한다. 고객 신청 화면과 관리자 판단 기준에 같은 정책을 적용한다.
- 가입 화면에서 승인된 필수 항목과 선택 수신 동의를 구분해 제공하고, 동의가 필요한 항목의 문서 버전·동의 일시·선택 결과를 저장한다. 기존 회원의 동의 이력은 실제 기록에 근거하며 추가 동의가 필요한 경우 운영 정책에 따라 안내한다.
- **인수 기준** — 필수 동의가 누락된 가입은 서버가 거부하고 선택 수신을 거절해도 가입할 수 있다. 게시 내용과 가입 기록에서 문서 버전을 확인할 수 있으며, 배송·반품 신청 결과가 공지된 정책과 일치한다. 담당자가 원문과 적용 조건을 확인한 뒤 게시한다.

## 출시 승인 기준

- [ ] STOCK의 실재고 등록과 P0의 인수 기준을 완료하고, 구매자·관리자 브라우저 시나리오 증거를 남긴다.
- [ ] 모의 PG로 결제 중복·타임아웃·복구를 포함한 종단 시나리오를 통과하고, 운영 반영 전 결제 환경 설정을 확인한다.
- [ ] 엄격한 `./scripts/harness test`의 상태 확인 실패가 남은 NC-TEST-001을 해소하고 전체 테스트를 통과한다. `./scripts/harness check`의 결과와 남은 기준선은 사유와 함께 검토한다.
- [ ] 임시 MySQL 8.4에서 Flyway와 JPA 검증, 기존 주문 이행, 백업·복원을 확인한다. 테스트는 실제 Toss Payments·S3를 호출하지 않는다.
- [ ] 운영자가 배송·취소·반품·환불 정책, 고객 안내 문구, 미확정 거래 확인 및 대응 절차를 승인한다.

구현에는 기존 Controller → Service/Facade → Repository 흐름과 `SuccessMessage`, `NanacocoaException`, `ErrorCode`를 적용한다. 스키마 변경은 새 Flyway 버전으로 추가하고 결제·재고·배송 경합은 집중 테스트와 평가 카탈로그에 연결한다. 로그와 검증 증거에는 결제 키, 세션 값, 고객 주소·연락처 원문을 남기지 않는다.
