## 목표와 현재 상태

회원이 주소록에 배송지를 등록·수정·삭제하고 기본 배송지를 지정한다.
바로 구매와 장바구니 복수 상품 checkout에서 기본 배송지를 자동 입력하거나
저장된 다른 배송지를 선택하고 직접 입력할 수 있다. 주소록 변경은 기존 주문에 영향을 주지 않는다.

준비 시점 Member.address는 하나의 문자열이며 회원 프로필 조회·수정은 비밀번호 본인 확인을
요구한다. 구조화된 주소록·기본 배송지 API는 없다. checkout은 회원 이름만 자동 입력하고
우편번호·기본주소·상세주소를 조합해 기존 주문의 shippingAddress에 저장한다.
기존 바로 구매·장바구니·주문 제출 키와 결제 복구를 재사용한다.

준비 이후 feature/36에서 아래 주소록 API·화면과 V12를 구현했다. 준비 기록의 API 미변경 상태와 구분한다.

## 화면 동작과 확정한 기본값

- 회원 전용 주소록 관리 화면과 마이페이지 진입점을 추가한다. 주소록 사용은 로그인·소유권을
  요구하며 기존 회원정보 API의 비밀번호 본인 확인을 완화하거나 우회하지 않는다.
- 주소록은 회원 프로필의 주소·전화번호와 독립적이다. 기존 문자열 주소를 자동 분해·이행하지
  않으며 프로필·가입·주소록을 서로 자동 동기화하지 않는다. 첫 진입은 빈 주소록이다.
- 최초 배송지는 기본 배송지로 등록한다. 이후 추가 시 기본 지정 여부를 선택하고 기본값은
  미선택이다. 기본 배송지 삭제 후 다른 주소를 자동 지정하지 않는다. 기본값 없이 사용 가능하다.
- 기본 삭제 후 주소록이 남아 있는 경우 추가 배송지도 자동 기본값으로 만들지 않는다.
  모든 주소를 삭제한 뒤 다시 처음 등록하는 주소는 기본으로 지정한다.
- checkout 기본 배송지 자동 입력은 사용자가 선택한 기본값이다. 새 주문서에서 배송 정보
  입력을 시작하지 않았을 때만 수령인·연락처·우편번호·기본/상세주소를 한 번 채운다.
  기존 이름 자동 입력은 사용자 편집으로 취급하지 않지만 사용자가 어떤 배송 필드든 편집하면
  늦게 도착한 기본값을 적용하지 않는다. 폼을 다시 비워도 자동 재적용하지 않는다.
- 저장된 다른 배송지 선택은 명시적인 폼 교체 행동이다. 기존 직접 입력을 덮어쓸 수 있음을
  선택 화면에서 안내하고 선택한 항목을 적용한다. 이후 직접 수정은 해당 주문서에만 반영한다.
- 기본값 없음·주소록 비어 있음·조회 실패를 구분한다. 실패해도 직접 입력을 사용할 수 있고
  조회 재시도는 사용자 행동으로 시작한다. 지연·재시도 응답도 이미 편집한 폼을 덮어쓰지 않는다.
- checkout에서 수정한 주소를 자동 저장하지 않는다. 주소록 등록·수정·삭제·기본 지정은
  명시적 사용자 행동이며 주문 버튼으로 주소록을 변경하지 않는다.
- 주문 제출 키가 있으면 기존 주문 조회·복구를 우선한다. 이미 접수한 주문의 배송 정보는
  주소록이나 현재 폼으로 바꾸지 않는다. 재전송은 최초 주문의 배송 정보와 같은 요청을 사용한다.
- 로그인 복귀는 고정된 허용 화면의 조회만 수행한다. 로그인·재로그인으로 주소 저장·삭제·
  기본 변경·주문·결제를 자동 실행하지 않는다. 로그아웃·계정 전환·뒤로 가기 캐시에서
  이전 회원 주소를 표시하거나 선택 문맥을 재사용하지 않는다.

## API·영속성 계약

로그인한 본인 주소록 목록·등록·수정·삭제·기본 지정 API를 추가한다. 리소스는
`/api/members/me/shipping-addresses`로 구분하고 회원 ID를 요청으로 선택하지 않는다.
GET 목록, POST 등록, PUT /{id} 수정, DELETE /{id} 삭제, PUT /{id}/default 기본 지정을
제공한다. 변경 요청에는 항목 또는 주소록 변경 버전을 검증하며 이전 버전은 409로
최신 조회를 요구한다. 타인과 없는 항목은 동일한 404로 처리한다. 모든 응답은 no-store다.

입력은 배송지명·수령인·연락처·우편번호·기본주소·선택 상세주소이며 주소 ID·버전·기본 여부를
응답한다. 우편번호 5자리, 기존 수령인/연락처 계약과 최종 주문 주소 500자 제한에 맞춰
검증한다. 외부 주소 검색 실패 시 수동 입력을 허용하고 가입·회원정보의 전화번호 계약을
이번 작업에서 바꾸지 않는다. 클라이언트 값만으로 소유권·기본값을 신뢰하지 않는다.

회원 단위로 기본 지정·최초 등록·삭제를 직렬화하고 항목 변경 버전과 함께 검증한다.
원자적으로 기존 기본값을 해제하고 새 기본값을 설정하며, 동시 등록·기본 변경·삭제로
중복 기본값이나 타인 주소 참조가 생기지 않도록 한다. 응답 유실 시 먼저 조회하고
쓰기 요청을 자동 재실행하지 않는다. 중복 클릭을 막고 등록 재전송으로 중복 주소가
생기지 않도록 요청 키를 저장·검증하는 계약을 후속 구현에 포함한다.

새 Flyway 버전으로 회원 소유 주소와 버전·기본 지정에 필요한 저장 구조를 추가한다.
적용된 V1~V11과 기존 회원·주문 배송 정보는 수정하지 않는다. 기존 테이블과 응답 형식을
대체하지 않으며 Controller → Service/Facade → Repository, SuccessMessage,
NanacocoaException·ErrorCode·전역 예외 처리를 유지한다.

기존 주문 API는 최종 배송 정보 값을 검증·스냅샷 저장하는 계약을 유지한다.
배송지 ID만 전달해 현재 주소를 나중에 참조하는 주문으로 바꾸지 않는다.
주문 생성 후 주소록 변경·삭제는 과거 주문·배송·RETURN 안내에 영향을 주지 않는다.

## 실패·보안·데이터 경계

모든 변경 요청은 세션 인증·CSRF를 요구한다. 타인 항목 존재 여부와 주소·연락처를
노출하지 않는다. 빈 목록·조회 오류·입력 오류·버전 충돌·인증 만료를 구분하고 실패를
성공 문구로 표시하지 않는다. 충돌 시 사용자 입력을 보존하며 최신 내용을 확인해 다시 제출한다.
기존 마이페이지 비밀번호 확인과 주문·결제 멱등성을 유지한다.

주소 원문·연락처·세션·토큰을 URL·로그·검증 증거에 남기지 않는다. 브라우저 저장소에
전체 주소록을 지속 저장하지 않으며 checkout의 계정 문맥을 재사용할 때 소유자를 확인한다.
검증은 합성 배송지로 수행한다. 실제 Toss Payments·S3·운영 DB를 호출하지 않는다.

## 범위 밖과 준비 완료 조건

이메일 발송·비밀번호/아이디 복구는 ACCOUNT 후속이다. 소셜 로그인, 비회원 주소록,
기존 주소 자동 이행·프로필 자동 동기화, 외부 주소 서비스 변경·운영 활성화·배포는 제외한다.
ACCOUNT 전체를 완료 처리하지 않고 배송지 준비 다음에 계정 복구, 이후 DISCOVERY를 유지한다.

PRD·이슈·추적 브랜치와 제품/출시 인덱스 연결, 사용자 파일 보존 대조,
문서·diff·전체 check 결과 분류 및 준비 실행 기록 완료 보관으로 준비를 완료한다.
준비 이후 별도 사용자 요청으로 구현·기능 검증을 진행했다. 문서는 로컬 미커밋이며 커밋·push·PR·병합은 미수행이다.

## 구현 계약·검증 결과 · 2026-11-22

[구현 실행 기록](../exec-plans/completed/issue-36-shipping-address-implementation.md),
[운영·API 계약](../runbooks/shipping-addresses.md).

V12는 shipping_addresses·shipping_address_books·shipping_address_registrations만 추가한다.
회원 잠금과 주소록 revision·항목 version을 검사한다. 기본 주소는 회원별 단일 포인터이며
소유권 복합 FK가 타인 주소 지정을 차단한다. 등록 키에는 정규화 입력의 SHA-256만 기록한다.
수정·등록 Details는 address 객체로 받고 등록은 expectedRevision·makeDefault·Idempotency-Key,
수정/기본 지정은 expectedVersion·expectedRevision, 삭제는 두 버전을 query로 받는다.
성공은 HTTP 200과 기존 SuccessMessage로 revision·checkoutAccount·items를 반환한다.
등록 재전송은 revision 검사보다 먼저 같은 키/내용을 확인하며 삭제 후에도 재등록하지 않는다.
X-Checkout-Account는 브라우저 계정 전환의 쓰기를 거부하며 소유권은 세션으로 결정한다.
