- 상태: 구현

- 선행 작업: [세션 보안 PR #15](https://github.com/JooonWooKim/nanacocoa-service/pull/15),

## 배경과 범위

[커머스 출시 PRD](commerce-launch-prd.md)의 PAY 후속 작업이다. checkout에서
주문은 저장됐지만 응답이 유실되면 재제출할 수 있다. 현재 `POST /api/orders`는
호출마다 주문 번호를 만들고 재고를 예약한다. 한 회원의 같은 주문 제출 시도는
동시 요청, 응답 유실, 새로고침, 재로그인 뒤에도 주문 하나와 최초 재고 예약 한 번으로
수렴해야 한다.

회원 바로 구매의 주문 생성과 재진입을 다룬다. 운영자의 미확정 거래 조회, 고객의
취소·반품·환불, 장바구니, 운영 PG 활성화는 후속 작업이다. 기존 결제 승인·취소의
멱등성 키, 재고 해제, 주문 만료, 결제 재시도 계약은 유지한다.

## 작업 범위와 인수 기준

| 작업 항목 | 구현 범위 | 인수 기준 |
| --- | --- | --- |
| 주문 제출 API | `POST /api/orders`에서 회원별 `Idempotency-Key`를 요구한다. 요청은 기존 주문 DTO를 사용하고 최초 생성과 재제출을 구분한다. | 최초에는 201, 같은 키·같은 내용은 200과 동일 주문 번호를 반환한다. 같은 키·다른 내용은 409, 인증된 요청의 누락·잘못된 키는 400이다. 다른 회원과 키가 겹쳐도 주문 정보를 공유하지 않는다. |
| 원자적 저장과 재고 | 데이터베이스에서 회원과 제출 키 조합을 유일하게 저장한다. 주문·품목·최초 재고 예약을 같은 트랜잭션으로 처리한다. | 동시 제출과 커밋 후 응답 유실에도 주문·예약이 각각 한 번만 생긴다. 실패 시 부분 주문이나 예약, 키 선점이 남지 않는다. 기존 주문은 이행 전후에 조회할 수 있다. |
| 구매 화면과 다시 조회 | checkout에서 첫 POST 전에 제출 키를 보관한다. 응답을 받지 못했다면 같은 시도를 조회하거나 같은 키로 다시 제출한다. | 중복 클릭·타임아웃·새로고침·재로그인 뒤 같은 주문을 찾는다. 확정되지 않은 응답만으로 새 키, 새 주문, 새 결제 요청이 생기지 않는다. |
| 결제·만료 경계 | 복구한 주문의 서버 금액과 주문·재고 상태로 진행 가능한 행동을 판정한다. | 결제 확인 중·완료·취소·만료 주문은 주문 상세나 기존 상태 확인 경로로 보낸다. 재제출 자체로 예약 연장, 결제 승인, PG 호출이 일어나지 않는다. |

## API 계약

- `POST /api/orders`: 로그인과 기존 세션 CSRF 보호를 요구한다. 헤더 값은 표준
  UUID 문자열로 제한하고 형식 오류를 서버에서 처리한다. 성공은 기존
  `SuccessMessage<OrderResponse>`를 사용한다. 200 재제출 응답에는 기존
  주문 번호·저장 당시 금액·품목과 조회 시점의 주문·재고 상태를 담는다.
  `canStartPayment`는 서버 시각 기준으로 미결제 주문의 기존 예약이 유효할 때 참이다.
- 요청 일치는 상품 ID와 수량을 ID 순서로 비교하고, 배송 정보는 주문 저장과 같은
  규칙으로 비교한다(앞뒤 공백 제거, 빈 배송 요청사항은 값 없음으로 처리). 기존
  주문 스냅샷을 비교에 사용한다. 브라우저 가격이나 현재 상품 가격으로 일치를
  판정하지 않는다. 내용이 다르면 전역 오류 형식으로 409를 반환하며 기존 값을
  응답에 노출하거나 변경하지 않는다.
- `GET /api/orders/submission`: 인증된 회원이 같은 헤더로 자신의 커밋된 제출
  결과를 조회한다. 주문을 찾으면 200과 기존 주문 응답을 반환한다. 본인에게
  해당 키가 없으면 404, 키 누락·형식 오류는 400이다. 미인증은 401이며 외부 PG를
  호출하지 않는다. 다른 회원의 키 존재 여부는 드러나지 않는다. 404는 현재
  커밋된 결과가 보이지 않는다는 뜻이며 이전 요청의 실패를 확정하지 않는다.
  주문 응답은 브라우저나 중간 캐시에 저장하지 않는다.
- checkout은 두 API에 세션 응답의 `checkoutAccount`를 `X-Checkout-Account`로
  보낸다. 식별자가 현재 인증 회원과 다르면 서버는 `ORDER_06` / HTTP 409를 반환한다.
  이 식별자는 재로그인 전후의 계정 일치 여부를 확인하는 값이다.
- 기존 Service의 인증 재확인, 재고 검증, 공통 응답·오류 처리를 사용한다.
  잘못된 품목, 재고 부족 등 기존 생성 오류의 의미를 유지한다. 같은 키의 결과가
  이미 있다면 현재 재고나 상품 가격을 다시 검사하기 전에 기존 제출을 판정한다.

## checkout 동작

- 주문 본문 검증과 기존 결제 가능 설정 확인 후, 첫 POST 직전에 생성 키를
  탭의 세션 저장소에 기록한다. 키, 복구에 필요한 상품 식별자, 로그인 전후
  같은 회원인지 비교할 수 있는 불투명 식별자만 남긴다.
  배송지·연락처·요청사항 원문은 새로 저장하지 않으며, 생성 키를 URL에 넣거나
  결제 승인 키로 재사용하지 않는다.
- 중복 클릭은 화면에서 제어한다. 타임아웃, 응답 유실, 새로고침 또는 세션 만료
  뒤에는 결과를 먼저 다시 조회한다. 조회에 아직 결과가 없으면 동일한 내용을
  다시 입력해 같은 키로 제출할 수 있다. 내용 불일치 시에는 기존 주문 확인을
  안내한다. 계정이 바뀌면 기존 키를 사용한 자동 재제출이나 결제 재개를 하지
  않는다. 결과를 확인할 수 없는 동안 자동으로 새 시도를 시작하지 않는다.
- 복구한 주문이 결제 가능한 상태면 주문 번호와 서버 확정 금액을 표시하고 구매자가
  결제를 이어갈 수 있게 한다. 대기 상태이거나 결제 가능하지 않으면 본인 주문
  상세에서 최신 상태와 허용된 다음 행동을 확인한다. 확정된 검증 실패 후 입력을
  수정하거나, 사용자가 이전 주문을 확인한 다음 별도 구매를 명시적으로 시작할
  때 새 키를 발급한다.

## 데이터와 동시성

- 새 Flyway 버전으로 제출 키와 회원별 유일 제약을 추가한다. 과거 주문은
  키가 없는 상태로 보존한다. 제출 키는 해당 주문과 함께 보존해 예약이
  만료되더라도 같은 키가 다른 주문을 생성하지 않게 한다.
- 데이터베이스가 복수 앱 인스턴스에서 동시 쓰기를 제어한다. 같은 회원·키의
  요청을 상품 잠금과 재고 검증 전에 직렬화하고, 대기한 요청은 잠금을 얻은 뒤
  선행 트랜잭션이 커밋한 주문을 확인한다. 이 순서로 마지막 재고가 이미 예약된
  경우에도 같은 시도는 품절 오류 대신 기존 주문을 찾는다. 기존 상품 ID 오름차순
  잠금과 재고 트랜잭션 경계를 유지한다.

## 검증 계획

- API 통합: 미인증·CSRF, 키 누락·형식, 일치·불일치, 타인 키 조회,
  가격·재고 변경 후 재제출, 취소·만료 뒤 동일 주문 조회를 검증한다.
- 임시 MySQL 8.4: 별도 트랜잭션의 동일 키·동일 내용 및 동일 키·다른 내용 요청,
  마지막 재고 한 개, 주문 저장 실패 후 재시도, 별도 키로 동일 상품 주문,
  기존 데이터 이행을 검증한다. 주문 행과 예약 수량을 함께 대조한다.
- checkout: 응답을 잃은 경우, 중복 클릭, 새로고침, 세션 만료 뒤 로그인,
  계정 변경, 복구된 주문의 결제 가능 여부를 확인한다. PG와 이미지 저장소는
  모의 어댑터를 사용한다.
- 관련 집중 테스트와 `./scripts/harness check`를 실행하고 결과를 평가
  카탈로그와 실행 계획에 연결한다. 로그와 증거에 제출 키, 결제 키, 세션 값,
  배송 정보 원문을 기록하지 않는다.
