# 마이페이지 주문 목록·상세 조회 PRD

- 상태: 조회 및 SHIP 연동 구현 완료 · RETURN 연동 대기
- 관련 이슈: [GitHub #10](https://github.com/JooonWooKim/nanacocoa-service/issues/10)
- 상위 명세: [커머스 출시 PRD의 ORDER 항목](commerce-launch-prd.md#order--주문-목록과-상세)

## 목표와 범위

구매 회원이 마이페이지에서 본인 주문을 찾고, 주문 당시 구매·배송 정보와 현재 결제 결과를 확인한다. 기존 주문 API의 생성·재고 예약·미결제 취소·검수 재입고에 더해 목록·상세 조회와 그 화면을 제공한다. 택배사·송장 조회와 취소·반품·환불 신청 흐름은 상위 PRD의 SHIP과 RETURN이 제공하는 상태 및 허용 행동을 연결한다.

## 화면 요구사항

| ID | 기능 | 인수 기준 |
| --- | --- | --- |
| ORDER-01 | 주문 내역 진입 | 마이페이지에서 주문 목록을 열고 각 주문의 상세로 이동한다. 상세에서 목록으로 돌아가면 기존 페이지를 다시 열 수 있다. |
| ORDER-02 | 목록과 페이지 나누기 | 본인 주문을 최신순으로 표시한다. 각 행에는 주문 번호, 주문 일시, 대표 상품, 주문 합계, 주문 상태가 있다. 미결제·취소 주문도 포함한다. |
| ORDER-03 | 조회 상태 안내 | 조회 중에는 진행 상태를 표시한다. 주문이 없을 때와 조회에 실패했을 때를 구분하고, 오류 시 같은 목록 페이지 또는 같은 상세를 재조회할 수 있다. 마지막 페이지에는 다음 이동을 제공하지 않는다. |
| ORDER-04 | 주문 상세 | 주문 번호·일시·상태·총액, 주문 당시 상품별 이름·단가·수량·품목 금액과 수령인·연락처·배송지·배송 요청사항을 확인한다. 새로고침·재로그인 후에는 서버의 최신 상태를 조회한다. |
| ORDER-05 | 결제 결과와 재조회 | 미결제, 결제 확인 중, 결제 완료, 실패와 기존 결제 취소 진행·완료를 저장 상태에 맞게 표시한다. 확인 중에는 결과 다시 조회를 제공한다. 이 동작은 상세 조회만 수행하며 승인이나 새 결제를 제출하지 않는다. |
| ORDER-06 | 배송과 사후 처리 연동 | SHIP 연동 후 배송 상태·택배사·송장 번호와 제공된 조회 링크를 표시한다. RETURN 연동 후 취소·반품·환불 진행을 표시하고 서버가 현재 허용한 신청만 제공한다. 연동 전에는 확인 가능한 주문 당시 배송 정보와 기존 결제 결과를 제공한다. |
| ORDER-07 | 로그인과 본인 주문만 조회 | 세션 만료 시 표시 중인 주문 데이터를 지우고 로그인으로 안내한다. 로그인 후 동일 목록 페이지 또는 상세로 돌아간다. 타인 주문과 없는 주문에는 동일한 안내를 표시한다. |

## 조회 계약과 데이터

| 인터페이스 | 조회 계약 |
| --- | --- |
| `GET /api/orders?page=0` | 로그인 회원의 목록. 페이지 번호는 0부터 시작하며 기본 0, 페이지당 20건. 주문 생성시각 내림차순과 주문 레코드 ID 내림차순을 사용해 동일 시각의 순서를 고정한다. 현재 페이지와 다음 페이지 존재 여부를 반환한다. 범위 밖 페이지는 빈 결과, 음수·잘못된 형식은 400을 반환한다. 여러 품목이면 저장 순서상 첫 품목을 대표로 사용한다. |
| `GET /api/orders/{orderId}` | 공개 주문 번호로 본인 주문의 구매 당시 정보와 현재 주문·결제 상태를 반환한다. 주문 소유 조건을 조회에 포함하고 권한 실패와 미존재 모두 동일한 404와 `NOT_FOUND_ORDER`를 반환한다. |
| 공통 | 미인증 요청은 401, 성공 응답은 `SuccessMessage`를 사용한다. 회원 식별자는 인증 세션에서 얻는다. 목록에는 전화번호·배송지를 포함하지 않는다. 결제 키, 멱등성 키, 제공자 오류 원문은 화면과 응답에서 제외하고 개인 주문 응답은 캐시하지 않는다. |

- 주문 당시 값은 `Order`와 `OrderItem`에 저장된 정보를 읽는다. 상품명 변경, 가격 변경, 회원 주소 변경과 무관하게 구매 기록이 유지되어야 한다. 기존 주문에 저장된 값이 비어 있으면 정보 없음으로 표시하고 현재 회원 주소로 채우지 않는다.
- 결제 표시는 주문 상태와 해당 주문의 결제 기록을 함께 해석한다. 확정된 승인·취소 결과와 진행 중인 승인·취소를 우선 표시하고, 유효한 결제가 없는 주문은 최신 확정 실패를 표시한다. 승인 후 보상 취소로 미결제 상태에 돌아온 주문은 결제 실패로 표시하며 고객 환불 완료로 표현하지 않는다. 결제 시도 기록이 없는 경우 현재 주문 상태를 표시한다.
- 기존 마이페이지 본인 확인은 유지한다. 주문 조회는 로그인과 주문 소유권을 요구한다. 로그인 복귀 대상은 같은 사이트의 주문 목록·상세 경로로 제한하고 복귀 후 소유권을 다시 확인한다.
- 기존 영속 데이터를 사용한다. 조회 요청은 읽기 전용으로 처리하고 주문·재고·결제 상태를 변경하거나 외부 결제 제공자를 호출하지 않는다. 서버 구성은 `Controller → Service → Repository`를 따른다.

## 검증과 완료 조건

| 검증 | 사례 |
| --- | --- |
| API 통합 | 주문 없음, 첫·다음·마지막 페이지, 같은 생성시각의 주문 정렬, 잘못된 페이지, 본인 주문 상세 성공, 미인증 401, 타인 주문과 미존재 주문의 동일한 404를 검증한다. 목록 응답에 배송 개인정보가 없는지 확인한다. |
| 데이터·결제 회귀 | 상품명·가격 및 회원 배송지 변경 뒤에도 주문 당시 값이 유지되는지 확인한다. 배송 정보가 비어 있는 기존 주문, 결제 기록 없음, 실패 후 재승인, 확인 중 후 승인, 취소 확인 중, 보상 완료를 검증한다. |
| 브라우저 | 마이페이지 → 목록 → 상세 → 목록 이동, 오류 후 재시도, 상세 새로고침, 세션 만료 후 로그인 복귀, 결제 확인 중 상태 재조회를 검증한다. |
| 후속 연동 | SHIP·RETURN 반영 후 배송 정보와 신청 권한 표시가 서버 상태와 일치하는지 확인한다. |

기능 구현 시 관련 집중 테스트와 `./scripts/harness check`를 실행하고 결과를 기록한다. 결제 상태 검증에는 가상 회원과 모의 결제 제공자를 사용한다.
