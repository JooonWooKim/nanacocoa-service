## 목표와 현재 상태

가입·checkout·푸터에서 같은 승인 문서를 확인하고, 회원가입 시 실제로 제시한
문서 버전과 동의 결과를 보존한다. 필수 동의는 서버에서 검증하며 선택 이메일
수신 거절은 가입을 막지 않는다. 게시 정책과 배송·취소·반품의 실제 적용 조건을
운영자가 대조할 수 있어야 한다.

`SignupRequest`와 `AuthService`는 현재 정책 버전과 필수·선택 동의를 검증하고
회원과 가입 동의 이력을 같은 트랜잭션으로 저장한다. checkout의 Toss 약관은 PG 약관이며 서비스
자체 안내를 대신하지 않는다. RETURN은 `returns.policy`의 승인 정보·버전·안내·조건이
갖춰져야 신규 신청·처리를 허용한다. POLICY 게시가 RETURN을 자동 활성화하지 않는다.

사용자는 승인 대기 구조와 저장소 파일·재배포 방식을 선택했다. 이 문서는 승인 원문이
아니며 원문·필수 항목·판매자와 문의처·배송비·반품 기간과 비용을 임의 확정하지 않는다.
기술 구현을 완료했으며 게시·운영 활성화는
아래 승인 선행 조건을 충족한 뒤 진행한다.

## 범위와 화면 동작

- 서비스 약관, 개인정보 안내, 판매자·문의처, 배송 범위·요금·출고 기준,
  취소·반품·환불 안내를 제공한다. 안내 문서와 동의가 필요한 항목을 구분하고
  필수·선택 여부는 승인된 문서 목록에 따른다. 모든 안내를 일괄 필수 동의로 취급하지 않는다.
- 공개 `policies.html`에서 문서 제목·버전·적용일·본문을 확인한다. 가입 화면,
  checkout과 기존 푸터·배송/반품 안내 진입점을 실제 문서로 연결한다.
  결제 금액과 배송비 계산, 기존 Toss 약관 동의 방식은 이 기능에서 변경하지 않는다.
- 가입 화면은 정책 조회가 끝난 뒤 승인된 동의 항목을 필수·선택 순서로 보여준다.
  필수 동의는 미선택으로 시작하고 선택 이메일 수신은 기존 기본값인 거절을 유지한다.
  서버 검증 전에도 필수 누락을 안내하지만 서버 검증을 대체하지 않는다.
- 모바일 가입 폼은 테두리 입력란·비밀번호 확인/표시·분할 휴대전화·전체 폭 가입
  버튼을 사용한다. 이메일 아이디와 필수 주소, 기존 가입 API·비밀번호 8~72자 계약을
  유지하며 소셜 가입 버튼은 추가하지 않는다. PR #4의 카카오 우편번호 공통 함수를
  재사용하고 우편번호·기본주소·상세주소를 기존 단일 주소 값으로 합친다. 검색 실패 시
  직접 입력할 수 있으며 전체 주소 500자 제한을 적용한다.
- 전체 동의는 선택 이메일 수신까지 포함하고 부분 선택을 표시한다. 각 화살표는
  동의 여부와 독립적으로 현재 제시 버전의 본문을 화면 안에 펼친다. 긴 원문은
  내부 스크롤하며 일반 텍스트로 렌더링한다. 조회 실패 시 재시도하고 정책 교체 시
  이전 본문 응답과 선택을 재사용하지 않는다. 동의가 필요 없는 안내는 링크로 유지한다.
- 정책 조회 실패·게시 준비 중에는 가입 제출을 보류하고 안내와 재조회를 제공한다.
  문서 버전이 바뀌면 새 문서를 표시하고 관련 동의를 다시 받는다. 가입·동의를
  자동 제출하거나 이전 동의 선택을 새 버전에 자동 적용하지 않는다.
- 실패 시 입력을 가능한 범위에서 화면에 유지하되 비밀번호를 브라우저 저장소에
  보관하지 않는다. CSRF 오류는 기존 공통 요청 경로와 안내를 재사용하고 사용자가
  다시 제출한다. 응답 유실 후 무조건 가입을 재전송하지 않고 로그인·중복 이메일 안내를 사용한다.
- 기존 회원의 로그인·주문 조회는 유지한다. 이번 범위는 가입 당시의 동의 기록이며
  마이페이지 이메일 수신 변경을 과거 가입 동의 기록에 덮어쓰지 않는다.

관리자 문서 편집 CMS, 전자서명, 기존 회원 강제 재동의·일괄 이력 생성, 배송비 계산,
반품 정책 변경은 제외한다. 승인 문서는 검토된 버전 자료를 배포하는 방식으로 관리한다.

## API와 저장 계약

Controller → Service → Repository 경계와 기존 `SuccessMessage`,
`NanacocoaException`, `ErrorCode`, 전역 예외 처리기를 재사용한다.
구현 시 요청 DTO는 기존 `dto.reqeust` 철자를 유지한다.

| 메서드·경로 | 계약 |
| --- | --- |
| `GET /api/policies` | 미인증으로 현재 게시된 승인 문서 목록을 조회한다. 문서 식별자·버전·제목·적용일·본문 경로와 동의 필요/필수 여부를 반환한다. 가입 가능 여부를 구분하며 문서 없는 상태를 가입 가능으로 간주하지 않는다. |
| `GET /api/policies/{documentCode}/{version}` | 승인 후 게시된 특정 버전의 문서만 반환한다. 과거 게시 버전은 이력 확인용으로 유지한다. 초안·미게시·미존재 문서는 동일한 404로 처리하며 내부 승인자 정보는 공개하지 않는다. |
| `POST /api/auth/signup` | 기존 회원 필드와 `emailReceiveConsent`를 유지하고 `consents`의 문서 식별자·버전·동의 결과를 추가한다. CSRF 필수. 성공은 기존 201·성공 응답을 유지한다. |

- 서버가 현재 가입에 적용할 승인 문서와 제출 목록을 대조한다. 필수 누락·거절,
  중복 문서·알 수 없는 항목·선택 수신 값과 동의 결과의 모순은 400으로 거부한다.
  현재 적용 버전과 다른 제출은 409로 재확인을 안내한다. 승인 문서가 준비되지
  않은 환경의 신규 가입은 503으로 보류하며 가입·이력을 일부 저장하지 않는다.
- 회원과 가입 동의 이력은 같은 트랜잭션으로 저장한다. 회원 참조·문서 식별자·버전,
  내용 해시·동의 여부와 서버 기록 시각을 보존한다. 선택 항목의 거절도 기록하고, 원문은
  버전으로 다시 확인할 수 있도록 게시 후 덮어쓰지 않는다.
- 기존 회원에는 실제 증거 없는 동의 일시·버전·결과를 채우지 않는다. 현재 이메일
  수신 값은 유지하며 이력 부재를 동의로 해석하지 않는다. 기존 회원의 추가 동의가
  필요하다면 별도 승인된 적용·안내 절차를 후속 범위로 준비한다.
- 새 Flyway 버전으로 저장 구조를 추가하고 기존 마이그레이션은 수정하지 않는다.
  구현 시 최신 이력의 다음 버전을 선택하고 `./scripts/harness migrations --accept-new`로 등록한다.
- 공개 조회는 승인된 문서만 반환하며 회원 동의 이력·개인정보·내부 승인 메모를
  노출하지 않는다. 이번 범위에서 타인 동의 기록 조회 API는 제공하지 않는다.

## 2026-11-20 파일 기반 정책 전환

현재/과거 약관은 배포 파일에서 읽은 불변 메모리 스냅샷으로 제공한다. 기존 정책 API와
가입 payload는 유지하며 문서·게시 DB 조회와 게시 잠금을 제거한다. DB에는 회원의
문서 코드·버전·해시·동의 결과·기록 시각을 저장한다. V10이 기존 이력을 이행하고
V9 원본 테이블과 기존 FK 값은 보존한다. 새 이력에는 문서 FK가 필요하지 않다.
파일 변경은 재시작으로만 반영하며 누락·오류·미승인 시 신규 가입을 보류한다.
과거 문서는 archivedDocuments에 보존하고 DB 원문으로 런타임 폴백하지 않는다.
배포 전 DB 원문 내보내기/해시 대조와 이전 배포 파일의 불변성 검사를 수행한다.
혼합 버전 서버의 동시 가입을 금지하며 전체 교체 후 명시적으로 활성화한다.
운영 전환/승인은 수행하지 않았다. [파일 전환 실행 기록](../exec-plans/completed/policy-file-storage.md).

## 승인·운영 활성화 선행 조건

| 승인 항목 | 확인할 내용 | 미확정 시 처리 |
| --- | --- | --- |
| 원문과 문서 목록 | 서비스·개인정보·선택 수신 안내, 동의 필요/필수 여부, 버전·적용일, 승인 주체와 기록 | 실제 정책 게시·동의 활성화 보류 |
| 판매자와 문의처 | 표시할 정보와 실제 운영 문의 경로 | 임의 정보나 작동하지 않는 링크로 대체하지 않음 |
| 배송 조건 | 범위·출고 기한·택배사·요금 및 서버 합계와의 일치 | 정책 게시와 실제 배송·요금 적용을 대조한 뒤 출시 승인 |
| 취소·반품·환불 | 기간·비용·부담 주체·회수·검수·환불 안내 및 RETURN 설정 | 게시 버전·안내와 `returns.policy`를 대조하고 불일치 상태에서 신규 운영 활성화 보류 |
| 기존 회원 | 추가 동의 필요 여부·적용 시점·안내 방식 | 과거 이력을 조작하지 않고 별도 운영 승인 항목으로 남김 |

POLICY 게시가 RETURN이나 실 PG를 자동 활성화하지 않는다. 기존 정책 비활성 상태,
거래 조회와 접수된 미확정 거래 복구의 경계는 유지한다. 운영 원문과 적용 조건은
운영 담당자가 승인하며 이 PRD와 GitHub 이슈 생성은 그 승인을 대신하지 않는다.

## 구현 시 검증과 준비 완료의 구분

- API·Service: 필수 누락·거절, 선택 거절 가입, 조작·중복·오래된 버전,
  승인 누락, 회원·동의 이력 저장 실패 롤백, 중복 이메일과 CSRF를 검증한다.
- 데이터: 기존 회원·이메일 수신 값 보존, 과거 문서 조회, 가입 기록 불변성과
  새 Flyway 이행·JPA 검증을 확인한다. 실제 MySQL 검증은 격리 환경을 사용한다.
- 브라우저: 가입·checkout·푸터 진입, 승인/미승인 상태, 조회 실패·재조회,
  문서 변경 후 재동의, 선택 거절 가입과 CSRF 재제출을 확인한다.
- 회귀: 로그인·세션 회전·마이페이지 본인 확인·이메일 수신 변경, 기존 checkout
  Toss 약관·결제 비활성, RETURN 조회·기존 복구 경계를 확인한다.
- 실제 Toss Payments·S3를 호출하지 않고 가상 회원·승인 문서 fixture를 사용한다.
  로그·증거에는 비밀번호·세션·토큰·고객 개인정보·결제 키를 남기지 않는다.
- 구현 후 관련 집중 테스트와 `./scripts/harness check`를 실행해 결과를 분류한다.
  NC-TEST-001의 health 실패는 별도 부채이며 BASELINED를 엄격 테스트 PASS로 보고하지 않는다.
- 기능은 feature/28 작업 트리에서 구현했으며 main 미반영이다. 신규 가입은
  `POLICY_SIGNUP_ENABLED=false`가 기본이고 승인 카탈로그와 명시적 활성화가 모두 필요하다.
  운영 원문·조건 승인과 운영 활성화는 수행하지 않았다.
- 구현·검증은 [구현 실행 기록](../exec-plans/completed/issue-28-policy-implementation.md),
  준비는 [준비 기록](../exec-plans/completed/issue-28-policy-preparation.md)에 구분해 기록한다.
