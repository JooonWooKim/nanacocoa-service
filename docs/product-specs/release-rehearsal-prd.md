## 목표

운영 담당자가 후보 하나를 지정해 그 커밋을 기동하고, 앱을 다시 띄운 뒤와 합성 DB를 복원한 뒤에 기록이 보존되는지 확인한다. 확인 결과를 같은 후보의 사전점검에 제출할 수 있다.

## 실행 계약

`./scripts/harness release-rehearsal --candidate <현재 HEAD 전체 SHA>`를 실행한다.
이미지와 공용 Compose를 빌드할 수 있는 로컬 Docker가 필요하다. 격리 환경의
가입 스위치와 실제 결제·PG 복구는 꺼져 있고 이미지 저장은 mock이다. 빌드에서
의존성과 베이스 이미지를 가져올 수 있다. DB와 Redis는 내부망에 둔다. 앱은 별도 브리지에서
루프백 포트를 게시하며 브리지의 IP masquerade를 끈다.

stdout은 JSON 한 객체다. 정상 완료는 PASS와 종료 코드 0, 후보·기동·테스트·정리 실패는
FAIL과 1, Docker를 사용할 수 없는 경우는 BLOCKED와 2다. HEAD 검증까지 통과한
경우에만 `check` 필드에 사전점검용 REHEARSAL 행을 발급한다. 운영 인수 증거는 기존
[사전점검 PRD](production-release-preflight-prd.md)의 별도 항목을 따른다.

## 검증

후보 불일치, 로컬 Docker 부재·원격 연결 거부, 격리 위반, 복원 불일치, 정리 실패와
사전점검 행 호환성을 Python fixture로 검증한다. 실제 Docker에서는 동일 명령으로
부팅, 가입 잠금·결제 차단, 앱 재시작, 덤프 복원과 정리를 대조한다. 실제 운영
환경 검증·판매자 승인·실거래 활성화는 출시 체크리스트에서 추적한다.

2026-11-27 기준 후보 `a818ec7`에서 Docker 리허설 8단계를 모두 통과했다.
사전점검은 생성된 `REHEARSAL`을 PASS로 인정했고, 리허설 행만 제출한 매니페스트의
종합 판정은 BLOCKED였다. Python 회귀 fixture 9개도 통과했다.
출시 후보를 선정하면 동일 명령으로 해당 SHA의 증거를 갱신한다.
