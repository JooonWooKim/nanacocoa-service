## 목표와 범위

회원이 가입 이메일로 복구 링크를 받아 새 비밀번호를 설정한다. 성공 후 모든 기존
로그인 세션을 만료시키고 직접 다시 로그인하게 한다. SMTP 어댑터와 모의 발송을
구현하며 실제 공급자 선정·발송 활성화·배포는 별도다. 아래 계약을 feature/38에서
로컬 구현했고 검증 증거는 이 문서와 구현 실행 기록에 남긴다. 문서는 로컬 미커밋이다.

이메일은 기존 로그인 ID이며 변경하지 않는다. 이메일을 잊은 경우의 아이디 찾기,
SMS·외부 본인 확인, 이메일 변경, 탈퇴, 마이페이지 비밀번호 변경 정책의 재설계는
제외한다. 기존 주문·결제·장바구니·배송지 데이터와 진행 중 거래를 초기화하지 않는다.

## API와 공통 보안 계약

`Controller -> Service -> Repository`를 유지하고 `SuccessMessage`,
`NanacocoaException`, `ErrorCode`, 전역 예외 처리기를 재사용한다. API는 익명
접근을 허용하되 JSON 쓰기 요청의 CSRF 검증을 유지한다. 응답은 `Cache-Control:
no-store`로 제공하고 CORS를 확장하지 않는다. 비밀번호·토큰은 응답에 포함하지 않는다.

| API | 입력 | 결과와 실패 처리 |
| --- | --- | --- |
| `POST /api/auth/password-recovery/requests` | `email` | 유효한 형식은 계정 유무·이메일별 제한·SMTP 결과와 무관하게 동일한 202와 일반 안내. 형식 오류는 공통 400 |
| `POST /api/auth/password-recovery/reset` | `token`, `newPassword`, `passwordConfirmation` | 성공은 공통 200 안내. 잘못됨·만료·사용·철회된 토큰은 동일한 공통 400. 변경은 명시적 제출 때만 수행 |

요청 안내는 “입력한 이메일로 복구 안내를 받을 수 있는 경우 메일이 발송됩니다.”로
통일한다. 회원 이름·이메일 일부·계정 유무·발송 완료 여부를 표시하지 않는다.
비밀번호는 기존 8~72자 규칙과 BCrypt의 UTF-8 72바이트 상한을 함께 검증하고 확인값
일치를 서버에서 검사한다. 오류·DB 장애 시 기존 비밀번호와 토큰 사용 상태는 유지한다.
응답 유실 뒤 자동 재전송하지 않으며 새 비밀번호로 로그인하거나 복구를 다시 요청하도록 안내한다.

## 요청 제한·발송·토큰

- 기본값은 정규화한 이메일별 60초 간격·1시간 5회 발송, 클라이언트 IP별 1시간
  20회 요청이다. 이메일별 제한은 존재하지 않는 이메일에도 동일하게 적용하고
  항상 같은 202를 반환한다. IP 제한만 계정과 무관한 공통 429를 반환한다.
  제한은 서버에서 원자적으로 적용하며 다중 인스턴스·재시작으로 초기화되지 않는다.
  프록시 신뢰 설정 없이 전달된 IP 헤더를 신뢰하지 않는다.
- 요청 처리 시간에 계정 조회·SMTP 지연이 직접 반영되지 않도록 제한된 비동기
  실행 경로에서 계정 조회·토큰 생성·발송을 수행한다. 큐 포화 등 전체 처리 불가는
  계정 조회 이전에 공통 503으로 처리하며 이메일별 실패 이유는 외부에 공개하지 않는다.
- 202는 접수 안내이며 배달 보장이 아니다. 이번 기본 구현은 서버 재시작이나
  SMTP 결과 불명확 시 메일을 자동 재발송하지 않는다. 사용자는 제한 시간 이후
  명시적으로 다시 요청한다. SMTP 연결·읽기 제한 시간을 두고 발송 오류는 비식별
  운영 지표로 구분한다. 토큰 생성 DB 트랜잭션 안에서 SMTP를 호출하지 않는다.
- 운영 기본값은 복구 비활성·실발송 비활성이다. 준비되지 않은 환경은 계정 유무와
  무관하게 공통 이용 불가 안내를 제공한다. 테스트 프로필에서만 모의 발송을 켠다.
  SMTP 인증 정보는 환경 설정으로 주입하고 저장소·브라우저에 포함하지 않는다.
- 링크는 검증된 서버 설정의 HTTPS 기본 URL로 만든다. Host·전달 헤더·사용자
  redirect 값으로 생성하지 않는다. 격리 테스트만 명시적 localhost HTTP를 허용한다.
- 토큰은 암호학적 난수 32바이트 이상, 기본 유효기간 30분, 회원별 일회용이다.
  DB에는 토큰 해시·발급 credential 해시·회원 연결·만료·사용/철회 상태를 저장하고 토큰 원문을 저장하지 않는다.
  원문은 발송 작업의 메모리에만 두며 운영 로그·추적·예외·API 응답에서 제거한다.
- 같은 회원의 재발급은 직렬화하며 새 토큰을 발급하면 이전 미사용 토큰을 철회한다.
  늦게 도착한 이전 이메일은 사용할 수 없다. 발송 실패·결과 불명확 시 기존 토큰을
  되살리지 않으며 다음 명시적 요청으로 새 링크를 발급한다.
- 비밀번호 변경과 토큰 소비·나머지 토큰 철회·세션 세대 갱신은 같은 DB 트랜잭션으로
  처리한다. 동일 회원의 토큰 발급·복구·일반 비밀번호 변경을 경합 검증하고,
  비밀번호가 변경되면 이전 credential에 발급된 복구 토큰은 사용할 수 없게 한다.
  동시 재설정 중 하나만 성공하며 실패 시 모든 상태를 롤백한다.

## 세션과 저장 구조

로컬 구현은 신규 Flyway V13으로 복구 토큰·요청 제한 기록과 회원의 인증 세대 값을
추가한다. V1~V12 checksum은 보존하고 V13만 등록했다. 기존
마이그레이션을 수정하지 않고 회원·주문·동의·장바구니·배송지 데이터를 보존한다.

로그인 시 인증 세대를 세션에 고정하고 인증 요청마다 서버의 현재 세대와 비교한다.
복구 성공 커밋 뒤 시작한 요청은 다른 인스턴스·관리자 세션을 포함해 이전 세대를
허용하지 않는다. 세대 정보가 없는 기존 세션도 재로그인을 요구한다. 검증 경로가
불가능하면 이전 세션을 신뢰하지 않는다. 커밋 전 이미 시작한 요청을 소급 취소한다고
간주하지 않으며, 기존 결제 콜백은 재로그인 후 저장된 주문 조회로 복귀한다.

기존 세션에는 새 세대를 자동 주입하지 않는다. 마이페이지 재확인 상태도 더 이상
사용할 수 없어야 한다. 새 비밀번호로 로그인하면 기존 세션 ID 회전·CSRF 재발급
규칙을 따른다. 일반 비밀번호 변경의 기존 세션 정책은 바꾸지 않되 복구 토큰은 철회한다.

## 화면 동작

- 로그인의 비밀번호 찾기를 복구 요청 화면에 연결한다. 아이디 찾기는 별도 본인 확인
  기능인 것처럼 표시하지 않고 “아이디는 가입 이메일입니다”라는 안내를 제공한다.
- 요청 중 중복 제출을 잠그고 서버 응답 전 발송 성공을 표시하지 않는다. 새로고침·
  뒤로 가기·로그인 복귀는 요청을 자동 재실행하지 않는다. CSRF 만료 시 재획득하고
  명시적 재제출을 요구한다. 입력값과 오류 안내는 접근 가능하게 연결한다.
- 복구 링크는 정적 재설정 화면의 URL fragment로 토큰을 전달한다. 초기 실행에서
  메모리로 옮긴 뒤 `history.replaceState`로 제거한다. 재설정 화면은 제3자 스크립트·
  추적·외부 자원을 사용하지 않고 `Referrer-Policy: no-referrer`를 적용한다.
  방문·미리보기·GET만으로 토큰 소비나 비밀번호 변경이 발생하지 않는다.
- 토큰 없는 직접 방문·제거 후 새로고침은 메일 링크 다시 열기/새 복구 요청으로 안내한다.
  성공 시 메모리 토큰과 비밀번호 입력을 지우고 로그인으로 안내한다. 페이지 이탈·
  뒤로 가기 복원 시 입력을 지우며 늦은 응답이 민감한 폼이나 성공 상태를 되살리지 못한다.
- 알 수 없는 토큰과 만료·사용·철회 토큰은 같은 재요청 안내를 제공한다. 로그인 상태의
  다른 계정과 혼동하지 않게 현재 계정의 주소·주문 등을 복구 화면에 표시하지 않는다.

## 인수 시나리오와 증거

아래 기술 시나리오는 로컬 구현에서 PASS다. 서버·DB·모의 SMTP·JavaScript·실제
HTTP·Chrome 증거를 조합했고 운영 공급자 실발송·배포 인수와 구분한다. 세부 결과는
아래 증거 표에 기록한다. main 반영은 미수행이다.

| ID | 시나리오 | 기대 결과·증거 |
| --- | --- | --- |
| RECOVERY-01 | 알려진/없는 이메일, 형식 오류, 요청 반복·동시 요청 | 동일 202 본문·상태, 회원별 제한 은닉, IP 제한 429, 제한 원자성·재시작/다중 인스턴스 유지, SMTP 지연이 접수 응답을 지연시키지 않음 |
| RECOVERY-02 | 모의 메일·SMTP 수신기 성공/거절/타임아웃, 비활성·큐 포화 | 신뢰 URL, 토큰 해시만 영속화, 동일 접수 안내, 실제 외부 메일 호출 0, 비식별 오류 증거 |
| RECOVERY-03 | 정상 재설정·비밀번호 정책·확인값 불일치 | 명시적 POST만 변경, 구 비밀번호 거부·신규 로그인 성공, 비밀번호 응답/로그 노출 없음 |
| RECOVERY-04 | 만료 경계·변조·사용·재발급된 이전 링크·메일 순서 역전 | 같은 오류 안내, 이전 토큰 부활 없음, 변경 없는 DB 대조 |
| RECOVERY-05 | 동일/다른 토큰 동시 제출, 일반 변경과 경합, DB 실패 | 회원당 유효한 한 번의 변경, 비밀번호·토큰·세대 원자성, 실패 전체 롤백 |
| RECOVERY-06 | 여러 기기·인스턴스·관리자 세션·프로필 재확인 | 성공 커밋 후 모든 이전 세션 접근 차단, 자동 로그인 없음, 재로그인·CSRF 정상 |
| RECOVERY-07 | 익명·CSRF 누락/만료·교차 출처·Host 변조 | 익명 복구 가능, 쓰기 CSRF 강제, 계정/토큰 노출 없음, 신뢰 URL만 사용 |
| RECOVERY-08 | 링크 미리보기·GET·재방문·이탈·늦은 응답·응답 유실 | 조회로 상태 변경 없음, URL/저장소/캐시/폼 보호, 자동 재전송·거짓 성공 없음 |
| RECOVERY-09 | H2·격리 MySQL 8.4 이행·동시성·재시작 | 기존 데이터 보존, JPA 검증, 한 번 소비/제한/인증 세대 영속성 일치 |
| RECOVERY-10 | 로그인·일반 비밀번호 변경·장바구니·배송지·주문·결제 회귀 | 기존 기능 유지, 재로그인 후 조회만 수행, 진행 거래 중복·자동 변경 없음 |

테스트는 합성 회원·가상 이메일·모의 SMTP와 기존 모의 PG를 사용하며 실제 SMTP·
Toss Payments·S3를 호출하지 않는다. Java·JavaScript 단위/통합, 실제 HTTP, 실제
브라우저 흐름을 구분한다. 브라우저 도구 장애는 자동화 통과와 별개의 BLOCKED다.
