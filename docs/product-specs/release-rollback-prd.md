## 목표

후보 배포 시점의 사전 백업을 사용해 이전 버전이 다시 기동하고 기존 합성 거래를 조회할 수 있는지 확인한다. 운영 담당자는 실제 출시 후보와 되돌릴 이전 SHA를 지정해 기술 검토에 참고한다.

## 실행 및 증거 계약

`./scripts/harness release-rollback --previous <이전 전체 SHA> --candidate <후보 전체 SHA>`를 사용한다.
후보를 체크아웃하고 로컬 Git에 이전 커밋도 확보한다. 두 커밋은 공용 배포 템플릿과
합성 회원·주문 조회 계약을 지원해야 한다. Docker는 임시 컨테이너 세 벌을
사용한다. 앱은 실행 단계에 맞춰 시작·중지한다. 덤프와 원시 서비스 응답은 결과에 포함되지 않는다.

stdout은 비식별 JSON 결과다. 종료 코드는 PASS 0, FAIL 1, BLOCKED 2다. 검증에 사용한
커밋·완료 단계와 이유를 기록한다. 이 결과는 운영 `ROLLOUT` 담당자의 검토 자료다.
트래픽을 연 뒤 발생한 거래 보존, 실제 복구 지점, 중지 판단과 배포 승인은 기존 운영 인수에서 확인한다.

## 검증

격리 MySQL 8.4에서 후보와 이전 앱을 실제 기동한다. 후보가 적용한 새 Flyway 이행이
없는 경우와 있는 경우를 확인하고, 후보 기동 실패, 손상된 백업·데이터 불일치,
정리 실패를 회귀 테스트로 확인한다.

2026-11-27 실제 main `ca07e71` → `074f591`과 임시 저장소에 V19를 추가한 후보 모두
Docker 리허설 8단계를 통과했다. 두 실행에서 복원한 이전 앱으로 결제 완료 주문을 조회했고,
합성 회원·상품·주문·주문 항목·결제·동의가 일치했다. 신규·기존 Python 회귀 각 9개가
통과했고 전체 하네스는 기존 예외로 BASELINED다.
