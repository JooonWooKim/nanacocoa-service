## 목표와 범위

운영자가 승인·승인 보상·결제 취소 결과가 미확정인 거래를 찾고, 기존 복구
절차로 한 건씩 재확인하며 저장된 결과를 확인할 수 있게 한다. 관리자 운영 화면과 API를 구현했으며 운영 활성화와 출시 승인은 별도 절차다.

결제 환경 분리(PR #17), 주문 제출 멱등성(PR #21), 기존 주문·재고·배송 경계를
재사용한다. 신규 취소·반품 접수, 반품 정책, 일괄 복구, 임의 성공·실패 확정,
PG 키 입력, 운영 결제 활성화 설정 변경은 포함하지 않는다. 여기서 환불은
기존 결제 취소와 승인 보상의 미확정 결과를 의미한다.

## 화면 동작

- 관리자용 `payment-operations.html`을 기존 관리자 화면의 탐색 경로에 연결한다.
  화면 진입만으로 PG를 호출하거나 복구를 실행하지 않는다.
- 기본 목록은 미확정 거래 전체다. 승인 확인·승인 보상·취소 확인 유형,
  정확한 주문 번호로 필터링하고 페이지를 이동한다. 재시도 예정 시각이 미래인
  거래도 표시한다. 오래된 거래부터 `createdAt`, ID 순으로 안정적으로 정렬한다.
- 목록은 유형, 내부 거래 ID, 주문 번호, 금액, 상태, 대기 시작 시각,
  재시도 횟수·예정 시각을 표시한다. 대기 시작은 해당 결제 또는 취소 레코드의
  생성 시각이다. 상세에서는 주문·결제·취소·재고 상태와 안전한 오류 안내,
  복구 가능 여부·보류 사유를 추가한다. 주문·재고 상태는 조회 정보다.
- 운영자가 상세의 개별 복구를 눌렀을 때 PG 조회와 기존 승인 재시도·보상·취소가
  실행될 수 있음을 확인한다. 처리 중 버튼을 잠그고 완료 후 상세·목록을 다시
  조회한다. 자동 polling이나 새로고침에 의한 재실행은 하지 않는다.
- 빈 목록, 조회 실패와 재시도, 세션 만료 후 로그인 복귀, 관리자 권한 상실,
  CSRF 오류를 구분한다. 로그인 복귀 후에는 조회만 하고 복구를 자동 제출하지 않는다.
- 결제 비활성 시에도 조회할 수 있고 복구 버튼에는 비활성 사유를 표시한다.

## API 계약

모든 API는 현재 DB의 회원 관리자 권한을 확인한다. Controller는 하나의
애플리케이션 Service/Facade만 호출하고 기존 `SuccessMessage`,
`NanacocoaException`, `ErrorCode`와 전역 예외 처리를 사용한다.

| 메서드·경로 | 요청과 응답 |
| --- | --- |
| `GET /api/admin/payment-operations` | 선택 `kind`는 `VERIFY_APPROVAL`, `COMPENSATE_APPROVAL`, `CANCELLATION`; 선택 `orderId`는 정확히 일치 검색. `page=0`, `size=20` 기본, size 1~100. 항목과 페이지 메타데이터 반환 |
| `GET /api/admin/payment-operations/{type}/{id}` | `type=APPROVAL`은 payment ID, `type=CANCELLATION`은 cancellation ID. 완료 거래도 상세 조회 가능 |
| `POST /api/admin/payment-operations/{type}/{id}/reconcile` | 본문 없이 기존 거래 한 건의 복구 실행. CSRF 필수. 처리 후 상세 반환. 확정 상태 200, 여전히 미확정이면 202 |

목록 대상은 `PENDING` 승인 중 `recoveryAction != NONE`인 결제와 `PENDING`
취소다. 승인 보상은 별도 거래를 만들지 않고 결제의 `recoveryAction`으로 구분한다.
목록·상세 DTO는 내부 ID, 주문 번호, 유형, 금액, 관련 상태, 생성·갱신 시각,
재시도 정보, 안전한 오류 분류, `canReconcile`, 보류 사유를 제공한다.
결제 키, 모든 멱등성 키·fingerprint, PG transaction key, 회원 이메일·주소·전화번호,
취소 사유 원문과 저장된 예외·PG 응답 원문은 반환하지 않는다. 오류는 서버의
허용된 분류와 고정 안내 문구로 매핑한다. 알 수 없는 오류는 일반 안내로 표시한다.

미인증 401, 관리자 권한 없음 403, 미존재 거래 404, 잘못된 필터·ID 400을
반환한다. 잠금 경합과 재시도 시각 전·누락 실행은 409, Redis 장애·중단과 결제 비활성은 기존 503으로
처리한다. 오류 코드는 기존 의미가 맞는 코드를 재사용하고 필요할 때 기존
`ErrorCode`에 추가한다. CSRF 계약은 [세션 보안 PRD](session-security-prd.md)를 따른다.

## 복구·데이터·보안 경계

- 관리자 인가는 배송 관리처럼 세션 회원을 DB에서 다시 조회해 검증한다.
  일반 회원에게 목록·상세·복구 정보가 노출되어서는 안 된다.
- 조회는 DB만 읽는다. 수동 복구는 결제 연동 활성화를 검증하고, 자동 복구
  스케줄러 플래그와 독립적으로 실행한다. 자동 복구를 끈 환경에서도 명시적
  수동 복구는 가능하지만 결제 연동 자체가 꺼져 있으면 PG 호출·상태 변경 전 거부한다.
- `PaymentRecoveryService`의 거래별 복구 경계를 추출·재사용한다. 기존 배치의
  예외 격리 동작은 유지하고 수동 요청에는 잠금 실패·미존재·실행 보류를 전달한다.
  PG 조회와 재시도 동안 장기 DB 트랜잭션을 유지하지 않는다.
- 기존 `OrderPaymentLock`을 얻은 뒤 최신 상태와 `nextRetryAt`을 다시 확인한다.
  미확정이며 예정 시각이 도래한 거래만 실행한다. 예정 시각이 없는 미확정 거래는
  운영 점검 대상으로 표시하고 수동 실행을 보류한다. 이미 확정됐다면 PG 호출 없이
  현재 상세를 반환한다. 중복 요청도 같은 규칙을 적용한다.
- PG 조회 결과의 결제 키·주문 번호·금액 일치를 확인하고 기존 상태 전이,
  PG 멱등성 키, DB 잠금·트랜잭션 경계를 유지한다. 신규 결제나 취소 레코드를
  만들거나 강제로 결과를 확정하지 않는다. 결과가 불확실하면 재시도 정보를
  유지하고 재고를 임의 해제하거나 재입고하지 않는다.
- 수동 실행에는 운영자 내부 ID, 거래 유형·내부 ID, 시각과 결과 분류를 기존
  로깅 수단으로 남긴다. 요청 본문·세션·키·고객정보·외부 예외 원문은 기록하지 않는다.
- 이 단계는 기존 결제·취소 컬럼을 사용하며 스키마 변경을 요구하지 않는다.
  새로운 상태 전이와 자동 스케줄러 정책은 추가하지 않는다.

## 작업 항목과 인수 기준

| 작업 항목 | 구현 범위 | 인수 기준 |
| --- | --- | --- |
| 목록·상세 조회 | 미확정 유형, 주문 검색, 페이지, 재시도 정보 | 미래 재시도 대상도 조회되고 완료 후 최신 상세가 유지된다 |
| 개별 복구 | 기존 승인·보상·취소 복구 경계 재사용 | 올바른 PG 결과로 수렴하고 계속 불확실하면 확인 중으로 남는다 |
| 중복·경합 방어 | 주문 락 아래 상태·재시도 시각 재검증 | 중복 클릭·복수 관리자·자동 복구 경합에 승인·환불·재고가 중복 반영되지 않는다 |
| 권한·실패 처리 | DB 관리자 검증, CSRF, 환경 비활성, 안전한 DTO | 권한 없는 조회·실행이 거부되고 키·개인정보가 노출되지 않는다 |
| 관리자 화면 | 목록·상세·수동 실행·결과 재조회 | 새로고침·재로그인 후 조회 가능하며 복구는 명시적 클릭으로만 실행된다 |
| 회귀·운영 안내 | 모의 PG, 결제·재고·배송 회귀와 운영 절차 | 집중 테스트와 하네스 결과가 증거와 함께 분류된다 |

## 구현 시 검증과 운영 인수

- Controller·Service 통합 테스트: 미인증, 일반 회원, 권한 회수, CSRF 누락·오류,
  조회 조건·페이지, 미존재·완료 거래, DTO 민감 필드 비노출을 검증한다.
- 모의 PG 테스트: 승인 성공·확정 실패·타임아웃, 승인 보상, 취소 성공·실패·타임아웃,
  조회 불일치, 재시도 시각 전·후, 완료 거래 재전송, 결제 비활성을 검증한다.
- 동시성 테스트: 수동 요청끼리 및 스케줄러와 경합할 때 PG 멱등성 키 유지,
  예약 판매 확정·해제와 환불 최대 한 번 반영을 검증한다. 필요한 DB 잠금
  시나리오는 임시 MySQL 8.4에서도 확인한다. 실제 Toss Payments·S3는 호출하지 않는다.
- 브라우저에서 조회·검색·상세·개별 복구·오류·세션 만료 복귀를 확인하고
  화면과 DB의 주문·결제·취소·재고 결과를 대조한다.
- 관련 Gradle 집중 테스트와 `./scripts/harness check`를 실행하고
  PASS·FAIL·BLOCKED·SKIPPED·BASELINED로 분류한다. 기존 health 실패를 새 기능의
  통과 증거로 해석하지 않는다. 아키텍처·문서·마이그레이션·보안 검사를 유지한다.
- 구현 완료 시 결제 환경 운영 절차와 평가 카탈로그를 갱신한다. 운영자는
  점검 담당자와 문의 대응·이관 절차를 정한다. 이번 PRD는 운영 활성화를 승인하지 않는다.
