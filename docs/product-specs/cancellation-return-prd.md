## 목표와 범위

구매자는 본인 주문에서 출고 전 전체 취소 또는 출고 후 전체 반품을 신청하고,
운영자는 승인·반려, 회수·검수와 환불을 처리한다. 기존 주문·배송 조회,
결제 취소·복구 및 검수 재입고를 연결한다. 사용자 구현 요청에 따라 기술 구현을
진행했으며 승인 정책 설정이 없으면 신규 신청·처리를 차단한다. 정책을 임의 확정하거나
운영 사용을 승인한 것이 아니다. 준비 단계의 구현 착수 조건은 이 비활성 기본값 방식으로 변경했다.

미결제 주문 취소는 기존 흐름을 유지한다. 첫 범위는 주문 전체이며 부분 취소·환불·
재입고, 교환, 택배사 자동 회수 연동, 자동 정책 판정, 운영 결제 활성화는 제외한다.

## 정책 승인 선행 조건

다음 항목은 승인되지 않았다. 임의의 기간·요금·환불 공제액을 코드나 고객 안내에
넣지 않는다. 고객 운영·제품 담당자는 승인자·일시·정책 버전과 아래 결정을 기록한 뒤
이 문서와 운영 설정을 승인본으로 갱신한다. 기술 구현은 운영 정책 승인이 아니다.
설정 계약은 [취소·반품 운영 절차](../runbooks/returns.md)를 따른다.

| 결정 항목 | 확정할 내용 |
| --- | --- |
| 취소·반품 자격 | 신청 기한과 기준 시각, 상품별 제한·예외, 출고 중 신청 처리 |
| 비용과 환불 | 배송비·반품비·부담 주체·수납 방법, 환불 안내 시점. 결제액에서 비용을 공제해야 한다면 전액 환불 범위와 충돌하므로 구현 전에 범위를 재검토 |
| 회수·검수 | 회수 접수·완료 증빙, 미회수·파손·검수 불합격 처리, 재판매 가능 기준 |
| 운영 판단 | 출고 전 취소 승인·반려 기준, 반려 후 재신청, 문의·이의 제기 경로와 담당자 |
| 기존 주문 | LEGACY 재고·출고 미확인 주문 대조와 운영 이관 절차 |

## 화면 동작

- 구매자는 기존 `orders.html` 상세에서 신청 유형, 사유, 처리 이력 중 고객 공개 내용,
  반려 사유, 회수·검수 진행과 환불 확인 중·완료·실패를 확인한다. 주문·배송·
  신청·환불·재입고 상태를 구분한다. 서버가 허용한 신청만 표시하며 결제 승인
  확인 중이거나 출고 미확인인 주문에는 보류 사유와 문의 동선을 안내한다.
- 신규 운영 화면 `returns.html`은 주문 번호·유형·처리 상태 필터와 페이지 조회,
  상세·배송 기록·허용 작업을 제공한다. 승인·반려·회수·검수·환불 실행은
  운영자의 명시적 동작으로 수행하고 사유와 처리 이력을 남긴다.
- 신청 중 버튼을 잠그고 응답 유실 후 기존 요청을 조회한다. 새로고침·재로그인으로
  신청·환불을 자동 재제출하지 않는다. 빈 목록, 조회 실패·재시도, 권한 상실,
  세션 만료 및 CSRF 복구는 기존 세션 보안 계약을 따른다.
- 미확정 환불은 기존 `payment-operations.html` 상세·개별 복구로 연결한다.
  복구 화면에서 신규 취소를 만들지 않고, 복구 후 신청 화면을 다시 조회한다.

## API 초안

기존 `SuccessMessage`, `NanacocoaException`, `ErrorCode`와 전역 예외 처리를 사용한다.
Controller는 하나의 Service/Facade만 호출한다. 구매자 API는 주문 소유권을,
관리자 API는 현재 DB 관리자 권한을 검증한다. 모든 변경 요청에 CSRF를 적용한다.

| 메서드·경로 | 요청·응답 제안 |
| --- | --- |
| `POST /api/orders/{orderId}/return-requests` | `requestKey`(UUID), `type`(CANCELLATION/RETURN), `reason`. 저장된 신청을 포함한 OrderView 반환. 동일 키·동일 내용은 기존 신청, 같은 키·다른 내용은 409 |
| `GET /api/orders/{orderId}/return-requests` | 본인 주문 신청 이력과 현재 신청, 허용 행동·보류 사유 반환 |
| `GET /api/orders/{orderId}` 확장 | 기존 필드를 유지하고 신청 요약, 환불·재입고 상태, 허용 후속 행동 추가 |
| `GET /api/admin/return-requests` | 선택 `orderId`, `type`, `status`, `page=0`. 20개 단위 페이지 조회 |
| `GET /api/admin/return-requests/{requestId}` | 신청·주문·배송·환불·검수 이력, 버전, 허용 작업과 보류 사유 |
| `POST /api/admin/return-requests/{requestId}/actions` | `requestKey`(UUID), 필수 `revision`, `action`, `reason`, 검수 작업의 필수 `resellable`·`refundEligible`. 처리 후 상세 반환. APPROVE·REJECT·COLLECT·RECEIVE·INSPECT·REFUND·RESTOCK 구분 |

요청 키와 작업 fingerprint를 영속화한다. 응답에는 키·fingerprint를 노출하지 않는다.
상태 변경 결과는 200, 환불 결과 미확정은 202로 반환한다. 잘못된 요청은 400,
미인증 401, 관리자 권한 없음 403, 타인·미존재 주문/신청은 동일한 404,
버전·상태·중복 내용 충돌은 409, 결제 비활성 또는 기존 락 장애는 기존 503 계약을 따른다.
입력 길이 등 상세 검증은 기존 주문·배송의 사유 500자 및 UUID 규칙에 맞춘다.
OrderView는 `requests`, `allowedTypes`, `holdReason`, `policyGuidance`이며 주문 상세의
`returns`에도 같은 구조를 추가한다. 상세는 `revision`, `actions`, `refundStatus`
(NOT_STARTED/PENDING/SUCCESS/FAILED), `restockStatus`(NOT_STARTED/FAILED_INSPECTION/COMPLETED),
검수·환불 자격, 정책 버전·안내와 공개 범위의 이력을 반환한다.
고객 응답에서 운영자 내부 메모·회원 식별자·PG 오류 원문을 제외하고 결제 키,
PG transaction key, 멱등성 키, 세션 값을 어떤 응답·로그·증거에도 추가하지 않는다.

## 상태·데이터와 기존 흐름 연결

- 신청 처리 단계와 환불·재입고 결과를 분리한다. 취소는 신청 → 승인/반려,
  반품은 신청 → 승인/반려 → 회수 중 → 회수 완료 → 검수로 제안한다.
  환불은 미시작·확인 중·완료·확정 실패, 재입고는 미처리·검수 불합격·완료를
  구분한다. 검수 불합격의 환불 자격은 승인 정책에 따르며 자동으로 반려하지 않는다.
- 주문별 진행 중 신청은 하나만 허용한다. 다른 키의 중복 신청도 기존 진행 신청을
  안내하고 환불을 추가 생성하지 않는다. 종료 신청과 재신청 이력은 보존하며
  재신청 허용 여부는 승인 정책에 따른다. 과거 환불 완료 주문에는 새 환불을 시작하지 않는다.
- 신청·작업 이력에 주문, 유형·사유, 상태·버전, 처리자·시각, 정책 버전,
  검수 결과와 기존 결제 취소 거래의 연결을 저장한다. 상태와 작업 이력은 같은
  트랜잭션에서 저장한다. 새 Flyway 버전과 DB 제약을 추가하고 적용된 이력은 수정하지 않는다.
  기존 주문에 신청·동의·검수 기록을 추정 생성하지 않는다.
- 취소 신청 접수와 출고 확정은 같은 주문 행 잠금에서 재검증한다. 접수된 취소의
  판단·환불 진행 중에는 출고를 보류한다. 출고가 먼저 확정되면 취소 유형의 신규
  신청을 거부하고 정책에 따른 반품을 안내한다. 취소 반려 후 출고 가능 여부도 최신 상태로 판단한다.
- 기존 직접 결제 취소 API를 통한 운영 승인 우회를 방지한다. 새 환불 시작은
  해당 신청의 승인·검수·환불 자격을 서버에서 검증한다. 출고 후 환불은 승인된
  반품에만 허용하는 별도 애플리케이션 경계를 두고 기존 직접 취소의 출고 차단을
  전역 해제하지 않는다. 이미 접수된 취소의 재전송·복구는 계속 허용한다.
- 기존 `OrderPaymentLock`, 결제 행 → 주문 행 순서와 상품 ID 순 잠금을 유지한다.
  신청 접수·배송 처리는 주문 행만 잠그고, 주문 행을 잠근 채 결제 행 잠금을 역순
  요청하지 않는다. 환불 실행은 기존 결제 준비·완료 트랜잭션을 재사용하며 PG 통신 중
  DB 트랜잭션을 유지하지 않는다. 처리 중 상태·revision을 잠금 안에서 다시 확인한다.
- 환불 준비와 신청의 기존 취소 거래 연결을 원자적으로 저장한다. 연결된 거래의
  상태를 기준으로 표시하여 PG 성공 뒤 DB 반영 실패·프로세스 재시작·자동/수동 복구에도
  새 거래가 생기지 않게 한다. 불확실한 거래는 같은 PG 멱등성 키를 유지한다.
  확정 실패 뒤 재시도는 기존 거래 결과를 확인하고 운영자의 명시적 작업으로만 수행한다.
- 정책 미설정·비활성 시 신규 신청과 운영 처리는 RETURN_01/503으로 차단한다.
  본인·관리자 조회와 기존 결제 복구는 유지한다. 같은 신청·작업 키의 조회성 재전송은
  저장 결과를 반환한다. 환불 실행 API는 재전송에도 PG 활성화 검증을 먼저 수행하므로
  비활성 후 결과는 GET으로 확인한다. 접수 당시 정책 버전과 설정이 다르면 신규 처리를 보류한다.
- 결제 비활성 시 정책이 유효하면 조회와 신청 접수는 가능하되 환불 실행은 PG 호출·환불 상태 변경 전에
  503으로 거부한다. 결제 결과 확인 중에는 환불 완료나 재입고 완료로 표시하지 않는다.
- 환불 완료는 제공자 취소 결과가 검증·저장된 뒤 확정한다. 자동·수동 복구의
  결과도 같은 신청에서 조회한다. 재입고는 전체 취소 확정, 판매 재고, 운영자 검수
  적합을 모두 만족할 때만 기존 `OrderInventoryService`를 호출한다. 기존 재입고 API도
  이 검수 조건을 우회하지 못하게 한다. 미출고 취소도 운영자가 상품을 확인한 뒤 처리한다.
- LEGACY 또는 출고 미확인 주문은 신규 자동 취소·환불·재입고를 보류하고 기존
  배송 대조 절차로 이관한다. 기존 결제 취소·보상 복구는 유지한다.
- 새 직접 결제 취소는 RETURN_03/409로 신청 경로를 안내한다. 기존 취소 키와
  fingerprint가 일치하는 재전송만 허용하며 결제 비활성의 기존 503 계약을 유지한다.
  신청 도입 전 취소된 주문의 기존 수동 검수 재입고는 유지하고, 신청이 연결된 주문은
  직접 재입고 API에서도 해당 검수·환불 조건을 검증한다.
- 반려 신청은 활성 슬롯을 해제한다. 환불 완료 주문은 새 신청을 허용하지 않는다.
  구매자 화면은 서버에서 확인한 최신 반려 신청 ID별로 요청 키 저장 범위를 구분한다.
  동일 유형·사유의 새 재신청은 새 키를 사용하고, 같은 재신청의 응답 유실 재시도는
  기존 키를 유지한다. 최초 신청은 기존 저장 범위를 유지하며 서버의 allowedTypes를 따른다.
  반려 후 재신청·배송 중 반품·검수 불합격 환불은 승인된 정책 설정을 따른다.
  반품 기한은 배송 완료 시각, 허용된 배송 중 반품은 출고 시각부터 계산한다.

## 구현 시 검증과 출시 조건

- 정상 미결제 취소, 출고 전 취소 승인·반려, 출고 후 반품 승인·반려·회수·검수,
  검수 불합격, 환불 성공·확정 실패·타임아웃과 복구를 모의 PG로 재현한다.
- 본인·타인·미존재 주문, 일반 회원·관리자 권한 회수, CSRF 오류, 세션 만료·
  재로그인, 빈 목록·페이지·조회 오류, 안전한 DTO와 로그를 확인한다.
- 접수 응답 유실·동일 키 재전송·다른 키 중복·내용 충돌, 복수 운영자 동시 수정,
  출고와 신청/환불 경합, 직접 취소·재입고 우회 요청, 자동/수동 복구와 프로세스
  재시작을 검증한다. 환불과 재입고를 각각 최대 한 번으로 확인한다.
- 임시 MySQL 8.4에서 새/기존 데이터 Flyway·JPA 검증과 잠금·롤백·중복 제약을
  확인한다. 기존 주문·결제·재고·배송 집중 회귀와 구매자·운영자 브라우저 증거를 남긴다.
- 실제 Toss Payments·S3는 호출하지 않는다. 관련 집중 테스트와
  `./scripts/harness check`를 실행하고 PASS·FAIL·BLOCKED·SKIPPED·BASELINED로 분류한다.
  NC-TEST-001의 health 실패를 신규 기능의 통과로 취급하지 않는다.
- 구현 시 아키텍처·평가 카탈로그·운영 절차·생성 문서를 갱신한다. 출시 PRD에는
  준비, 구현·검증, main 반영, 정책 승인과 종단 검증을 각각 실제 상태로 기록한다.
