이메일·SMS·푸시, 미결제 주문 접수, 문의 답변 및 입고 알림은 후속이다. 기존 주문 상태와 결제·배송·환불 규칙을 유지한다. 기존 거래 이력은 알림함에 소급하여 채우지 않는다.

## 확정 기록과 게시 경계

- 결제 승인과 환불은 `PaymentTransactionalService`의 로컬 확정 경로에서 UTC 서버 시각을 남긴다. 정상 승인과 복구 승인은 동일 경로를 사용한다. 결제된 주문의 취소·반품 환불이 PG 확인과 DB 커밋을 마친 경우만 환불 알림을 만든다. 승인 보상 취소나 결제 대기·실패는 대상에서 제외한다. 정상 출고는 `ShippingService`의 최초 `SHIP` 기록을 대상으로 삼는다.
- V16에 기존 확정 레코드용 nullable 시각과 알림 처리·읽음 저장을 추가했다. 확정 시각은 기존 거래 상태와 같은 트랜잭션에 기록하며 재전송으로 덮어쓰지 않는다. 이전 레코드에 시각을 채우지 않는다. 선행 마이그레이션 체크섬과 주문 데이터는 보존한다.
- 알림 작업은 커밋된 확정 데이터를 읽어 소유 회원과 주문을 확인한다. 운영 설정의 활성화 기준 시각(UTC) 이상만 포함한다. 기본 비활성이며 활성화 시 기준 시각을 명시한다. 일시 중단 후에는 같은 기준 시각을 유지하고 아직 처리 기록이 없는 완료 건을 다시 찾는다. 목록 정렬에는 확정 시각과 ID를 사용한다.
- 일반 알림 처리는 거래 트랜잭션 밖에서 실행한다. 주문 ID와 이벤트 유형(`PAYMENT_COMPLETED`, `SHIPPED`, `REFUND_COMPLETED`)의 DB 유일 제약으로 처리 레코드를 한 건만 만든다. 인스턴스 간에는 처리 레코드를 잠그고 상태를 재확인한다. 게시 성공과 게시 상태 확정은 함께 저장한다. 결제·출고·환불 경로에는 게시·실패·재시도가 개입하지 않는다.
- 처리 상태는 `PENDING`, `PUBLISHED`, `FAILED`로 구분한다. 기본 작업 주기는 30초, 회당 최대 100건이고 실패는 다음 실행부터 최대 총 3회 시도한 뒤 실패 대기로 둔다. 운영자는 `FAILED` 한 건을 명시적으로 다시 대기열에 넣을 수 있다. 수동 재시도는 다음 자동 시도 구간을 다시 시작하지만 총 시도 횟수는 보존한다. 게시 완료 건은 다시 처리하지 않는다. 게시 트랜잭션 실패는 별도 트랜잭션에서 시도 결과를 갱신한다. DB 장애로 기록 자체가 불가능하면 비식별 운영 로그로 확인하고 복구 후 미처리 건을 다시 읽는다.

## 화면·API 계약

마이페이지의 주문 관리 메뉴에서 알림함을 열고 미읽음 수를 확인한다. 내 주문에서도 알림함에 접근할 수 있다. 목록에는 알림 유형, 주문번호, 확정 시각과 읽음 상태를 표시한다. 상태·빈 목록·조회 실패를 구분하고, 클릭으로 내 주문을 열 때 기존 주문 소유권 검사를 유지한다. 읽음은 명시적 변경 동작으로 제공하고, 로그인 복귀는 조회만 실행한다. 주문별 알림은 거래가 확정됐다는 안내이며 최신 거래 상태의 기준은 내 주문 상세다.

| API | 동작 |
| --- | --- |
| `GET /api/notifications?page=0` | 회원 본인의 게시된 알림을 최신순 20건씩 반환한다. 페이지·다음 페이지 여부·미읽음 수를 반환한다. |
| `PUT /api/notifications/{id}/read` | 로그인 회원의 게시된 알림을 읽음으로 표시한다. 반복 요청은 기존 읽음 시각을 유지한다. |
| `GET /api/admin/notifications?page=0&status=FAILED` | 운영자 전용. 기본 실패 목록에 주문번호, 유형, 시도 횟수, 마지막 실패 코드와 시각을 제공한다. |
| `POST /api/admin/notifications/{id}/retry` | 운영자 전용. 실패 건 한 건을 다시 대기로 전환한다. 대기·게시 건은 작업을 중복 생성하지 않는다. |

기존 공통 응답·세션·CSRF·운영자 판정을 재사용하고 비공개 응답은 캐시하지 않는다. 공개·회원·운영 응답 및 로그에 배송지·결제 키·PG 오류 원문을 담지 않는다. 본인 알림의 유효하지 않은 ID는 타인 ID와 같은 404로 처리한다.
