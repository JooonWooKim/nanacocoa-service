# 배송관리 구현 PRD

| 항목 | 내용 |
| --- | --- |
| 상태 | 구현 완료 · 운영 정책 및 출시 연동 검증 대기 |
| 우선순위 | P0 · 첫 공개 출시 |
| 기준일 | 2026-11-15 작업 트리 |
| 대상 | 배송 운영자, 구매 회원 |

## 목표와 출시 범위

운영자가 결제 확정 주문을 찾아 출고하고 배송 완료를 기록할 수 있다. 구매 회원은
기존 주문 상세에서 현재 배송 상태와 조회 링크를 확인할 수 있다. 취소·반품 기능은
이 배송 기록을 기준으로 출고 전 취소와 출고 후 반품을 구분한다.

첫 출시안은 주문 전체를 한 번에 출고하고 주문당 유효한 송장을 하나 유지하는 방식이다.
운영자가 택배사와 송장을 입력하고, 택배사에서 배송 완료를 확인한 뒤 상태를 갱신한다.
분할 배송, 송장 자동 발급, 택배사 API 연동·자동 추적, 배송 알림, 취소·반품 신청 화면과
환불·재입고 처리는 후속 범위다.

상위 명세는 [커머스 출시 PRD의 SHIP 항목](commerce-launch-prd.md#ship--관리자-출고와-구매자-배송-조회)이다.
기존 본인 주문 목록·상세 조회에 배송 상태를 연결한다. 주문은 수령인·연락처·배송지·요청사항을 보관하지만 배송 상태와
송장 이력은 없다. [주문 목록·상세 PRD](order-history-prd.md)

## 화면 요구사항

| ID | 사용자 흐름 | 요구사항 |
| --- | --- | --- |
| SHIP-01 | 관리자 배송 목록 | 기본으로 출고 가능한 배송 준비 주문을 보여준다. 주문 번호와 배송 상태로 검색·필터링하고 페이지 단위로 조회한다. 행에는 주문 번호, 주문·결제·배송 상태와 출고 시각을 표시한다. 조회 중·결과 없음·오류를 구분하고 같은 조건으로 재조회할 수 있다. |
| SHIP-02 | 관리자 배송 상세·출고 | 주문 당시 품목과 수령인·연락처·배송지·요청사항, 결제 상태, 배송 이력을 보여준다. 출고 전 택배사·송장 번호·사유를 확인한다. 출고 등록 응답이 확정되면 해당 송장으로 물품을 인계한다. 출고 보류 주문에는 사유와 다음 행동을 표시한다. |
| SHIP-03 | 관리자 송장 정정·배송 완료 | 잘못 입력한 택배사 또는 송장 번호를 정정하고 사유를 기록한다. 배송 완료는 운영자가 택배사 결과를 확인한 후 기록한다. 상세에는 최초 등록과 정정 전후 값, 상태 전이, 담당자, 시각, 사유를 표시한다. |
| SHIP-04 | 구매자 배송 조회 | 마이페이지 주문 상세에 배송 상태를 주문·결제 상태와 별도로 표시한다. 출고 이후 최신 택배사·송장 번호·출고 시각과 지원되는 조회 링크를 보여준다. 링크 매핑을 사용할 수 없으면 택배사와 송장 번호로 조회할 수 있도록 복사 기능을 제공한다. 송장 정정 결과는 상세 재조회 시 반영된다. |

## 상태와 허용 동작

아래 상태는 배송 화면의 표시 기준이다. 출고 기록이 있으면 저장된 배송 상태를 표시한다.
출고 기록이 없으면 서버가 취소 확정, 출고 보류, 배송 준비, 출고 전 순서로 판정한다.

| 상태 | 조건 | 허용 동작과 고객 표시 |
| --- | --- | --- |
| 출고 전 | 미결제, 결제 확인 중 또는 승인 확정 실패 | 원래 주문·결제 상태에 맞는 안내를 표시한다. 출고 요청은 거부한다. |
| 배송 준비 | `OrderStatus.PAID`, 유효 결제의 `PaymentStatus.SUCCESS`, 판매 확정 재고(`SOLD`)가 모두 확인되고 보류 사유가 없음 | 관리자가 출고를 등록할 수 있다. 구매자에게 배송 준비를 표시한다. |
| 출고 보류 | 결제 취소 결과 확인 중, 출고 여부를 확인하지 못한 과거 주문, 또는 결제 확정 주문의 판매 확정 재고·배송 필수 정보 미확인 | 관리자가 보류 사유를 확인한다. 취소 결과 확인 중에는 재조회 안내를, 과거 주문에는 배송 확인 필요를 표시한다. |
| 배송 중 | 출고 가능 주문에 택배사·송장을 등록하고 출고를 확정함 | 관리자가 송장을 정정하거나 배송 완료를 기록할 수 있다. 구매자는 송장과 조회 링크를 본다. |
| 배송 완료 | 운영자가 배송 완료를 기록함 | 완료 기록을 유지하며 입력 오류에 대한 송장 정정을 허용한다. |
| 출고 전 취소 | 출고 기록 없이 주문 취소 또는 환불이 확정됨 | 출고를 차단하고 취소 결과를 표시한다. |

- 최초 출고 시각은 송장 정정으로 바뀌지 않는다. 정정과 배송 완료도 각각 이력에 추가한다.
  배송 중·완료를 배송 준비로 되돌리거나 출고 기록을 삭제하는 동작은 제공하지 않는다.
- 출고 등록은 시스템의 출고 전 취소 가능 구간을 닫는 시점이다. 운영자는 포장을 마친 뒤
  등록하며, 응답이 끊기면 주문 상세에서 등록 여부를 확인한 후 인계한다. 등록 후 인계에
  실패하면 운영자가 실제 물품과 택배사 상태를 대조해 처리하고, 고객에게 진행 상황을 안내한다.
- 출고 후 반품이나 환불이 확정돼도 출고 이력을 보존한다. 배송관리는 결제 승인·환불·재고 수량을 변경하지 않는다.

## 서버 계약과 데이터

- 관리자 조회는 검색 조건과 페이지 정보를 받고, 상세는 배송 이력과 현재 허용 동작을 반환한다.
  등록·정정 요청은 활성 택배사 코드, 택배사별 형식에 맞는 송장 번호, 사유를 요구한다.
  송장은 앞자리 0을 보존하는 문자열로 다루고, 조회 링크는 서버가 승인한 HTTPS 택배사
  주소와 인코딩한 송장으로 구성한다. 완료 기록에도 처리 사유를 남긴다.
- 구매자 배송 정보는 기존 `GET /api/orders/{orderId}` 응답에 추가한다.
  관리자 API는 로그인과 현재 DB 관리자 권한을 검사한다. 미인증은 401, 관리자 권한
  부족은 403으로 처리한다. 타인 주문과 없는 주문은 기존과 동일한 404로 응답한다.
  입력 오류는 400, 갱신할 수 없는 상태나 오래된 버전의 요청은 409로 응답하고 화면에서
  최신 상세를 다시 열 수 있게 한다.
- 운영자 쓰기는 세션 CSRF 보호를 적용한다. 구매자 응답에는 담당자·사유·과거 송장을
  담지 않는다. 관리자 목록은 배송 개인정보를 제외하고, 권한이 있는 상세 화면에서
  출고에 필요한 정보만 보여준다. 개인정보를 포함한 응답은 캐시하지 않으며 로그와
  검증 자료에 주소·연락처·송장·자격 증명 원문을 남기지 않는다.
- 배송 레코드는 주문과 일대일로 연결하고 상태, 현재 택배사·송장, 최초 출고·완료 시각,
  버전을 저장한다. 변경 이력은 담당자와 서버 기록 시각, 사유, 변경 전후 값을 포함한다.
  상태와 이력을 한 트랜잭션으로 저장한다. 같은 요청 키와 같은 입력의 재전송은 한 번만
  기록하고, 같은 키에 다른 입력을 보내거나 오래된 화면에서 갱신하면 충돌로 처리한다.
- 웹 경계는 `Controller → Service/Facade → Repository`를 따르고
  `SuccessMessage`, `NanacocoaException`, `ErrorCode`를 사용한다. 스키마 변경은
  새 Flyway 버전을 추가한다. 출시 기준 시점 이전의 주문은 기존 출고 여부를 자동으로
  판단하지 않는다. 운영자가 실제 결제·배송 기록을 대조할 때까지 출고를 보류한다.
  이미 출고된 주문은 확인된 기록만 이행한다. 미출고로 확인된 주문은 배송 준비 조건을
  충족할 때 출고할 수 있다. `LEGACY` 재고 상태의 주문은 운영자가 별도로 처리한다.
  [기존 재고 이행 정책](../runbooks/inventory.md)

## 결제 취소와의 경계

기존 `POST /api/payments/{paymentId}/cancel`은 결제 소유권과 결제 상태를 검사한다.
출시 시 이 경로의 새 취소 시작에도 출고 상태 검증을 적용한다. 이미 접수된 취소의
동일 요청 재조회·재처리는 기존 멱등성·복구 흐름을 따른다. 출고 후 환불은 RETURN의
검수와 환불 권한이 확인되는 경계에서 기존 결제 취소·복구 서비스를 재사용한다.
RETURN 연결 전에는 출고 후 직접 취소를 거부하고 고객에게 문의 경로를 안내한다.
출고 여부가 미확인인 과거 결제 주문의 새 취소 요청도 출고 기록을 대조할 때까지 보류한다.

출고 확정과 결제 취소 시작은 같은 주문의 DB 잠금 경계에서 최신 상태를 읽고 결정한다.
결제 잠금과 주문 잠금은 기존 결제·복구 경로와 일관된 순서로 취득한다.
취소가 먼저 접수되면 외부 요청 전에 `CANCEL_PENDING`을 저장해 출고를 차단한다.
출고가 먼저 확정되면 출고 전 취소 요청을 거부한다. 취소 응답이 불확실하면 보류를
유지하며, 확정 실패 후에는 최신 결제·재고 조건을 충족하는 주문만 다시 출고할 수 있다.

## 인수 기준

| 영역 | 검증할 시나리오와 기대 결과 |
| --- | --- |
| 출고·조회 | 관리자 검색·필터·페이지 이동 → 결제 확정 주문 출고 → 구매자 주문 상세 → 택배사 조회 → 배송 완료. 새로고침·재로그인 후에도 최신 상태와 송장이 표시된다. |
| 입력·정정 | 택배사·송장 누락, 지원하지 않는 택배사, 잘못된 형식은 400이다. 송장 앞자리 0이 보존되며, 정정 후 고객은 최신 값만 확인하고 운영자는 전후 값과 담당자·시각·사유를 확인한다. |
| 권한 | 미인증, 일반 회원, 권한이 변경된 관리자의 운영 API 호출과 잘못된 CSRF 토큰을 거부한다. 구매자는 본인 배송만 조회한다. 타인 주문과 미존재 주문 응답이 동일하다. |
| 결제·출고 경합 | 미결제·승인 대기·취소 대기·취소 완료 주문은 직접 API 호출에도 출고되지 않는다. 출고와 취소 시작의 양쪽 순서를 독립 트랜잭션에서 검증한다. 한쪽 성공 후 다른 쪽의 새 요청은 차단되며, 취소 타임아웃·복구 중에는 출고가 계속 차단된다. |
| 재전송·동시 수정 | 출고 응답 유실 후 동일 요청을 재전송해도 배송 레코드·이력이 중복되지 않는다. 관리자 두 명이 같은 버전을 수정하면 하나만 성공한다. 이력 저장 실패 시 배송 변경도 롤백된다. |
| 기존 주문·회귀 | 이전 DB 이행 후 과거 주문의 배송 기록이 임의로 생기지 않는다. 출고 여부 미확인 주문의 출고와 결제 취소를 차단한다. 본인 주문의 기존 배송지·결제 내역이 유지되며, 회원 배송지 변경은 주문 당시 정보에 영향을 주지 않는다. |

출시 전 모의 결제 제공자로 주문·결제·배송·취소 통합 시나리오를 검증하고, 임시 MySQL
8.4에서 새 Flyway 마이그레이션과 동시 요청을 확인한다. 운영자와 구매자 화면의
브라우저 증거를 남긴다. 관련 집중 테스트를 [평가 카탈로그](evaluation-catalog.md)에
연결하고 `./scripts/harness check` 결과를 기록한다. 배송 운영·제품 담당자의 정책
승인과 SEC의 세션 보호, RETURN의 출고 판정 연동을 첫 공개 출시 전에 검증한다.

운영 설정과 실제 처리 순서는 [배송 운영 절차](../runbooks/shipping.md)를 참고한다.
