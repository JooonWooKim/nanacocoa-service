## 사용자 흐름

담당자가 승인된 내부 Slack 채널에서 봇을 멘션해 화면의 요청 번호 또는 자동 복구 실행 번호를 전달한다. 수신 서비스는 요청을 등록하고, 별도 작업자가 같은 번호의 비식별 이벤트를 기존 `incident-evidence`로 조회한다. 담당자는 요청한 채널의 원래 스레드에서 실패 단계, 확인할 운영 절차, 권장 테스트를 본다. 증거가 부족하면 필요한 추가 증거가 안내된다.

첫 구현은 합성 이벤트와 모의 Slack 어댑터로 격리 검증한다. Spring Boot 쇼핑 애플리케이션과 독립된 수신·처리 경계로 두며, 기존 주문·결제 API와 Flyway는 그대로 사용한다. 외부 Slack 앱 설치, 운영 로그 연동, AI 분석·수정안 및 운영 배포는 각각 후속 범위다.

## 수신과 저장 계약

- 첫 입력은 `@봇 incident request <UUIDv4>` 또는 `@봇 incident run <UUIDv4>` 형식의 `app_mention`이다. 후보 SHA는 담당자가 구성한 증거 공급자가 결정한다. 외부 URL, 파일 첨부, 자유 문장 및 다른 인수는 처리하지 않는다. 봇 자체 이벤트, DM과 외부 공유 채널은 접수 범위 밖이다.
- 설정이 완전할 때만 수신을 켠다. 본문 크기를 제한하고 파싱 전에 원본 바이트 기반 Slack 서명과 요청 시각을 검증한다. 서명 검증을 통과한 `url_verification`은 제한된 challenge 응답만 쓰며 작업을 만들지 않는다. 일반 이벤트는 서명과 별도로 앱·워크스페이스·채널·요청자를 대조한다. [Slack 요청 서명](https://docs.slack.dev/authentication/verifying-requests-from-slack/) · [앱 멘션](https://docs.slack.dev/reference/events/app_mention/)
- 워크스페이스와 이벤트 ID 조합에 유일 제약을 두고, 영속화 이후 2xx를 반환한다. 저장 실패는 재전달 가능한 오류로 반환한다. 동일 키로 서로 다른 내용이 수신돼도 최초 등록 정보는 보존한다. 상태와 큐 저장소는 쇼핑 DB와 분리하며, 메시지 본문 대신 처리에 필요한 식별자, 명령 종류, 원래 스레드 위치와 상태만 보관한다. [Slack 이벤트 응답과 재전달](https://docs.slack.dev/apis/events-api/#responding-to-events)

## 자료 생성과 회신 계약

- 배포 후보 SHA와 일치하는 로컬 비식별 증거만 공급하고 `incident-evidence`의 기존 허용 목록과 결과를 재사용한다. 기준 불일치, 자료 누락, 비허용 필드는 각각 담당자가 구분 가능한 상태로 남긴다. 수신 데이터는 명령·저장소 경로·대상 환경을 고르는 데 사용하지 않는다.
- 회신은 서버가 관리하는 작업 번호·자료 생성 판정·고정 실패 단계와 절차·권장 테스트를 포함한다. 입력 원문과 링크, 요청 본문, 쿠키, 결제 키, 고객 정보, 증거 파일 자체는 회신하지 않는다. 답변의 채널과 스레드는 승인된 원본 이벤트에서 고정하고, 링크 미리보기를 끈다. [Slack 스레드 회신](https://docs.slack.dev/reference/methods/chat.postMessage/)
- 발송 전에 상태를 기록하고, 성공 응답을 저장해 재시작 시 중복 발송을 막는다. 수락 여부가 확정된 재시도 가능 실패는 제한된 횟수와 대기 시간 내에 재처리한다. 타임아웃이나 발송 후 성공 기록 전 중단으로 전달 여부를 모르면 `BLOCKED`로 남겨 담당자가 원래 스레드를 확인한다. Slack 메시지에 표시되는 PASS는 자료 생성 판정이다. 주문·결제 업무 상태와 검증 결과는 기존 화면과 하네스에서 확인한다.

## 인수 검증

- 정상 접수 시간, 잘못된 서명·오래된 요청·미승인 채널과 요청자, 동시 재전달, 저장 실패와 재시작을 모의 HTTP에서 확인한다.
- 재고 예약 실패·승인 미확정·자동 복구 실패 자료를 만들고 다른 번호의 이벤트 배제, 후보 불일치, 민감 값 비노출을 검증한다.
- 결과 회신 후 재처리, 비율 제한, 응답 유실·재시작 시 중복 방지 및 원본 스레드 고정을 확인한다. 격리 검증에서는 외부 Slack, 실제 PG·S3 및 운영 서버 호출을 차단한다.
- 회귀 검사는 `./scripts/harness check`와 기존 `incident-evidence` 테스트를 사용한다. 결과는 PASS·FAIL·BLOCKED·SKIPPED·BASELINED로 구분해 기록한다.

## 로컬 구현과 증거

Python 표준 라이브러리와 별도 SQLite 파일을 사용했다. 루프백 수신기가 서명된
합성 요청을 영속화하며, 별도 작업자가 기존 해결 자료 명령을 실행한 뒤 모의 회신을
원래 스레드와 함께 기록한다. 발송 확정과 자료 생성 결과는 각각 확인할 수 있다.

HTTP·작업자 테스트 12개에서 접수 시간과 권한, 동시 재전달, 큐 저장 장애,
작업자 재시작, 재고·미확정 승인·자동 복구 자료, 비율 제한과 응답 유실을 검증했다.
전체 Python 35개와 H2 Java 268개가 통과했다. 전체 하네스는 기존 구조·보안 예외를
유지한 `BASELINED`다. 실제 Slack 설치·회신과 운영 로그 연결은 후속 인수에 포함한다.
