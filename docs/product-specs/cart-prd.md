## 목표와 현재 상태

회원이 상품을 서버 장바구니에 저장하고 수량 변경·삭제·선택 후 복수 상품을
주문한다. 새로고침·재로그인 후에도 본인 장바구니를 확인한다. 결제 승인이
서버에서 확정되면 주문과 연결된 항목만 한 번 정리한다.

준비 시점의 `script.js` 상품 상세 담기 버튼은 `.cart-dot` 숫자와 버튼 문구만 바꾸고
저장하지 않는다. checkout은 단일 상품 ID와 수량에 결합되어 있다.
기존 주문 API의 `CreateOrderRequest.items`와 `OrderService`는 이미 복수 상품,
상품별 재고 잠금과 회원별 주문 제출 키를 지원한다. 이를 확장·재사용하며
완료된 P0 종단 검증을 다시 신규 기능으로 취급하지 않는다.

## 화면과 사용자 흐름

- 회원 전용이다. 비회원 담기는 로그인으로 안내하며, 로그인 완료 시 원래
  상품 또는 장바구니 화면을 조회한다. 로그인 복귀로 담기·주문·결제를 자동 실행하지 않는다.
- 상품 상세에서 담으면 서버 응답 후 개수와 완료 문구를 갱신한다. 장바구니
  아이콘은 실제 장바구니 화면으로 연결하고 개수는 전체 담긴 수량의 합으로 표시한다.
- 장바구니 화면은 상품명·이미지·최신 단가·수량·금액·판매 상태, 수량 변경·삭제,
  전체/개별 선택과 선택 합계를 제공한다. 재진입 시 구매 가능한 품목은 기본 선택하며
  선택 자체는 화면 상태로 유지한다. 품절·판매 중지 항목은 남겨 두되 선택 구매를 막는다.
- 선택이 없으면 주문 버튼을 비활성화한다. 선택 구매는 선택 항목·수량·버전과
  확인한 가격을 checkout에 연결한다. 브라우저 값은 가격·소유권의 신뢰 근거가 아니다.
- checkout은 복수 상품과 합계를 표시한다. 가격 변경은 최신 금액으로 갱신한 후
  재확인·재제출을 요구한다. 품절·부족·판매 중지·동시 수정은 항목별 안내 후
  장바구니로 돌아가 수정하도록 하며, 일부 항목만 조용히 주문하지 않는다.
- 기존 `checkout.html?id=...` 바로 구매와 기존 주문의 결제 재개·결과 조회를 유지한다.
  바로 구매는 장바구니 정리를 유발하지 않는다.

## API·영속성 계약

준비 이후 feature/34에서 아래 API·V11 스키마를 로컬 구현했다. 준비 당시 API 미변경 기록과 구분한다.

- 인증된 본인 장바구니 조회·담기·수량 변경·삭제 API를 추가한다. 회원 ID를
  클라이언트 선택값으로 받지 않는다. 조회는 상품 ID·이름·이미지·최신 단가·판매 상태,
  장바구니 항목 ID·수량·변경 버전을 제공하고 내부 재고 수량·결제 키는 제외한다.
- 같은 회원·상품은 한 항목으로 저장한다. 담기는 양의 정수 수량을 더하되 요청 키로
  같은 담기 재전송을 한 번만 반영한다. 같은 키의 다른 요청은 충돌로 거부한다.
  수량 변경은 절대 수량과 기대 버전으로 처리하며 삭제도 기대 버전을 검증한다.
  0·음수·소수·범위 초과·합계 overflow는 저장 전에 거부한다. 삭제는 별도 행동이다.
- 경합 시 기존 데이터에 덮어쓰지 않고 충돌을 안내한 뒤 최신 장바구니를 다시 조회한다.
  장바구니 담기는 재고 예약이 아니며 재고 부족 여부의 최종 판단은 기존 주문 생성이다.
- 기존 주문 생성 계약에 선택 장바구니 항목과 기대 버전·수량·확인 가격을 연결한다.
  기존 단일/복수 `items` 주문은 호환 유지하고, 장바구니 출처가 있는 요청은
  해당 항목과 items가 일치해야 한다. 서버가 소유권·가격·판매 상태·재고를 검증한다.
  재전송 조회는 기존 주문 제출 키와 최초 주문을 반환하며 새 주문·예약을 만들지 않는다.
- 회원·상품별 장바구니, 요청 재전송 방지, 주문 당시 항목 연결·정리 결과를 영속화한다.
  새 Flyway 버전으로 추가하고 기존 마이그레이션·주문 이력은 수정하지 않는다.
- `Controller → Service/Facade → Repository`와 기존 `SuccessMessage`,
  `NanacocoaException`, `ErrorCode`·전역 예외 처리를 사용한다.

## 결제 후 정리와 동시 변경

사용자 결정은 **주문 생성 후가 아니라 결제 승인 확정 후 정리**다.

- 주문 생성·재고 예약·PG 인증 redirect·승인 요청 시작·확인 중·실패·중단·만료는
  정리하지 않는다. 서버에 승인 완료가 기록된 주문만 대상으로 한다.
- 브라우저 콜백 실행 여부에 의존하지 않는다. 정상 승인과 기존 개별/자동 복구가
  같은 서버 정리 규칙을 사용한다. PG 네트워크 호출 중 DB 트랜잭션을 유지하지 않는다.
- 주문에는 당시 장바구니 항목 ID·버전·구매 수량을 고정한다. 승인 시 같은 항목과
  버전이면 구매 수량만 차감하고 0이면 삭제한다. 다른 품목·미선택 품목은 유지한다.
- 주문 후 추가·수량 수정 또는 삭제 후 재등록한 항목은 보존한다. 변경된 버전은
  정리 생략 결과를 기록하며 뒤늦은 콜백·복구가 다시 차감하지 않는다.
- 주문별 정리 결과와 항목 변경은 원자적으로 저장한다. DB 실패 시 정리 완료로
  표시하지 않으며 승인 거래를 새로 만들지 않고 정리만 멱등 재처리할 수 있어야 한다.
- 환불·취소는 정리했던 항목을 자동으로 다시 담지 않는다.

## 실패·보안·호환성

타인 항목의 존재나 수량을 노출하지 않는다. 모든 변경 요청에 세션 인증·CSRF를
적용하고 계정 전환 시 이전 회원의 선택/checkout 문맥을 사용하지 않는다.
조회 실패·빈 장바구니·변경 실패·동시 수정·세션 만료를 구분해 안내한다.
응답 유실 재전송은 같은 요청 키로 확인하며 새로운 담기를 자동 실행하지 않는다.
원문 고객 정보·세션 값·결제 키를 URL·로그·증거에 남기지 않는다.

비회원 저장·회원 병합, 옵션 상품, 쿠폰·배송비 정책 변경, 계정 복구·주소록,
부분 결제·부분 환불, 판매자 정책 승인·운영 활성화·배포는 범위 밖이다.

H2·격리 MySQL 8.4에서 저장·제약·마이그레이션·경합을 검증하고 Java·JavaScript,
모의 PG HTTP와 실제 브라우저로 화면/API/DB 결과를 연결한다. 실제 Toss Payments·S3는
호출하지 않는다. 브라우저 장애는 자동화 PASS와 분리해 BLOCKED로 기록한다.
새 의미 있는 테스트의 발견 목록은 검증 후 등록하며 실패 기준선을 완화하지 않는다.
