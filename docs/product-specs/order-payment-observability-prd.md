## 목표

주문·결제 처리 중 오류가 발생하면 구매자가 화면의 요청 번호를 문의에 알려줄 수 있다. 운영자는 번호로 서버 로그를 찾고 실패한 작업과 결과를 확인할 수 있다. 개별 복구와 자동 복구의 기록을 구분한다.

운영자가 그 번호를 기준으로 타임라인, 실패 단계, 관련 코드·운영 절차, 권장 테스트를 한 번에 확인할 수 있게 한다. 첫 버전은 이 자료를 만들고 담당자가 격리 환경에서 확인하는 데까지 제공한다.

참고 영상은 장애 접수, 자료 검색, AI 수정안, 변경 범위에 따른 테스트 실행, 실패 후 재검증과 비용 관리를 설명한다. 첫 버전에는 자료 검색과 테스트 선정을 적용하고, AI 분석과 외부 접수는 같은 자료를 재사용하는 후속 단계로 정의한다. [자료 검색·수정안·테스트 선정 구간](https://www.youtube.com/watch?v=ixPKbtwecz0&t=11s) · [재검증·비용 관리 구간](https://www.youtube.com/watch?v=ixPKbtwecz0&t=27s)

## HTTP·화면·로그 계약

- 대상은 `POST /api/orders`, `POST /api/payments/confirm`, `POST /api/payments/{paymentId}/cancel`, `POST /api/admin/payment-operations/{type}/{id}/reconcile`이다. 추적을 인증·CSRF 검사보다 먼저 시작해 거부 응답에도 번호를 제공한다. 각 요청은 서버가 만든 UUID를 사용하며 클라이언트가 보낸 번호를 응답이나 로그에 복사하지 않는다.
- 응답 헤더만 추가한다. 기존 응답 본문, 상태 코드, 세션·CSRF, 멱등성, 결제·재고 전이와 DB 스키마는 유지한다. 요청 수명에 묶인 로깅 컨텍스트는 성공·실패 모두 종료 시 정리한다.
- checkout과 운영 결제 화면은 대상 요청의 오류 응답에서 받은 유효한 번호만 기존 안내에 보탠다. 기존 오류 문구와 조회·복구 선택지를 유지한다. 새 작업이나 성공 화면에 이전 오류 번호를 남기지 않는다.
- 추적 로그는 서버 생성 번호, 고정 작업·실행 유형, 정해진 결과 코드, HTTP 상태 또는 복구 결과와 처리 시간만 사용한다. 주문·결제 ID가 들어간 원본 URL, 쿼리, 요청·응답 본문, 예외 원문, 쿠키·세션·인증 헤더, 고객 데이터와 결제·멱등성 키는 추적 로그에 복사하지 않는다. 기존 대상 경로의 진단 로그도 같은 유출 기준으로 점검한다.
- 자동 복구는 실행별 번호를 만들고 승인·취소·보상 등 처리 유형과 성공·보류·실패 상태를 제한된 값으로 기록한다. 수동 복구는 HTTP 요청 번호를 사용한다. 외부 관측성 연동과 새 운영 조회 API는 별도다.

## 장애 해결 자료 계약

- 하네스의 `incident-evidence`는 운영자가 준비한 UTF-8 JSON 파일과 `--request-id` 또는 `--run-id` 중 하나를 받는다. 파일에는 `candidateCommit`(40자리 SHA), `events`(배열), 선택 항목인 `changedPaths`(저장소 상대 경로 배열)를 넣는다. 커밋은 현재 체크아웃과 일치해야 하며, 각 명령에는 UUIDv4 하나를 지정한다.
- `nanacocoa.incident` 로거의 `INCIDENT_EVENT` 뒤 JSON에서 `kind`, `id`, `occurredAt`, `operation`, `result`, `durationMs`를 수집한다. `kind`는 `HTTP` 또는 `RECOVERY`이며, HTTP에만 `httpStatus`를 포함한다.
- 이벤트에는 추적 종류·번호, 발생 시각, 고정 작업·결과 코드, 해당하는 HTTP 상태 또는 복구 결과와 처리 시간만 넣는다. 입력 단계에서 알 수 없는 필드·값과 잘못된 형식을 검출하면 FAIL로 종료하고 고정된 사유만 반환한다. 결제·멱등성 키, 고객 정보, 세션, 원본 URL·본문·예외는 입력과 출력에서 제외한다. 다른 번호를 가진 이벤트도 입력 형식 검증을 거치지만 결과에는 포함하지 않는다.
- 출력 JSON에는 후보 커밋, 선택한 번호, 시간순 이벤트, 증거로 확인한 실패 단계, 관련 코드·운영 절차, 권장 테스트와 선정 이유를 담는다. 분류는 고정 작업·결과 코드와 저장소의 매핑을 사용한다. 이벤트 누락 또는 근거 부족은 BLOCKED로 표시하고 필요한 증거 유형을 알려준다. 자료 생성 PASS는 장애 해결 판정과 별도로 기록한다.
- 담당자가 같은 기준에서 작성한 수정 후보의 변경 파일 목록을 제공하면, 파일의 도메인에 맞는 회귀 테스트를 기본 목록에 추가한다. 변경 경로는 저장소 내부 경로로 한정하고 이름을 바꾸거나 이동한 파일은 기존·새 경로를 모두 확인한다. 공통 코드 또는 미등록 경로처럼 영향 범위를 확정하기 어려운 경우 전체 하네스와 격리 MySQL 검사를 안내한다.
- 담당자는 격리 환경에서 허용된 테스트를 실행하고 같은 기준 커밋, 수정 후보 식별자, 실제 테스트 결과를 함께 남긴다. 자료 생성 명령은 파일 조회와 안내만 수행한다. 결제 조회·복구가 필요한 운영 요청은 기존 운영 화면의 승인 및 권한 절차에서 처리한다.

| 합성 장애 | 자료에 포함할 절차 | 권장 테스트 |
| --- | --- | --- |
| 주문 제출 중 재고 예약 실패 | 주문 제출 멱등성과 상품 재고 잠금, 복수 상품 롤백을 확인 | `OrderServiceTest`, `InventoryIntegrationTest` |
| 결제 승인 결과 미확정 | 기존 거래 조회와 복구를 먼저 안내. 승인 재제출 여부는 저장 상태와 기존 복구 절차에서 판단 | `InventoryIntegrationTest`, `PaymentOperationsIntegrationTest` |
| 자동 복구 실패 | 해당 실행 번호의 승인·취소·보상 분류와 다음 복구 단계를 확인 | `PaymentOperationsIntegrationTest`, 작업 유형에 해당하면 `ReturnRequestIntegrationTest` |

결제·재고가 달라질 수 있는 후보는 기존 `./scripts/harness check`와 `./scripts/harness mysql-quality`를 격리 환경에서 실행한다. 권장 테스트가 나온 것과 테스트가 통과한 것은 별도 증거다. [미확정 결제 운영 절차](../runbooks/payment-environment.md)

## 후속 Slack·AI 연동

첫 후속 작업은 [Slack 장애 접수와 해결 자료 회신](slack-incident-intake-prd.md)이다. 모의 수신과 회신으로 기존 비식별 자료를 연결하며 운영 연결과 AI 분석은 각 후속에서 다룬다.

동일한 비식별 JSON을 승인된 Slack 접수와 AI 분석의 입력으로 재사용한다. AI는 근거 위치와 수정 후보 또는 추가 증거 요청을 제안하고, 담당자가 후보를 검토한 뒤 격리 테스트를 실행한다. 실패 후 재제안은 최초 제안 외 최대 두 번으로 제한한다. 제한된 모델·토큰 예산과 검증 결과를 기록하고, 한도 내에 검증되지 않으면 담당자에게 이관한다. 캐시·모델 선택은 비용과 소요 시간이 측정된 이후 조정한다.

## 검증 시나리오

- Java 통합·HTTP에서 성공, 401·403 및 CSRF 거부, 도메인 오류·5xx 응답의 번호와 로그를 대조한다. 동시 요청과 스레드·스케줄러 재사용에서 번호 간 섞임과 클라이언트 헤더 반사를 검사한다.
- JavaScript와 격리 브라우저는 유효한 헤더가 있는 오류, 헤더 누락·형식 오류, 네트워크 실패, 다음 요청 시 오류 번호 초기화, 불필요한 재제출 방지를 확인한다.
- 모의 PG에서 승인·취소·수동/자동 복구의 기존 상태 전이와 호출 횟수를 확인한다. 합성 민감 값이 예외·URL·제공자 응답에 있을 때도 추적 로그에 나타나지 않아야 한다.
- 합성 장애 세 가지에서 관련 로그·코드·절차·테스트를 확인한다. 다른 번호의 증거 제외, 타임라인 정렬, 근거 누락, 비허용 필드·값 거부와 오류 출력 비반사를 검증한다.
- 변경 경로가 알려진 경우 권장 테스트를 추가하고 미등록 경로는 전체 검사로 안내하는지 확인한다. 승인 결과 미확정 자료를 만들고 조회 절차를 확인할 때 승인·취소·재입고 API가 새로 호출되지 않아야 한다.
- 기존 H2 하네스, 격리 MySQL, 문서·diff 검사 결과를 분리한다. 실제 Toss Payments·S3, 운영 로그·운영 배포는 사용하지 않는다.
